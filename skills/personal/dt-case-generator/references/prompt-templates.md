# DT用例生成提示词模板

本文档提供了DT用例生成过程中常用的提示词模板,可以直接使用或根据具体情况调整。

## 1. 代码理解提示词

### 基础版本
```
请帮我理解一下 <代码路径> 的代码并且生成准确的类图并使用标准的UML图表示,要求需要识别关键的接口,结构体和枚举定义。请检查你生成的类图文档中的接口、结构体、枚举,这些都要与现存代码仓的头文件中已有的定义完全一致。结果保存到 <输出文件名>.md
```

### 增强版本(包含依赖检查)
```
请帮我理解一下 <代码路径> 的代码并且生成准确的类图并使用标准的UML图表示,要求需要识别关键的接口,结构体和枚举定义。

请特别注意:
1. 识别所有对外接口(用于后续打桩)
2. 识别所有关键数据结构
3. 识别枚举类型及其取值
4. 检查所有依赖的头文件

请检查你生成的类图文档中的接口、结构体、枚举,这些都要与现存代码仓的头文件中已有的定义完全一致。如果发现不一致,请明确指出。

结果保存到 <输出文件名>.md
```

## 4. 打桩识别提示词

### 基础版本
```
请把目录下所有的TEST_F中需要打桩的流程按照一下的格式进行打桩模块使用的接口使用CPPMOCK进行打桩

具体的接口需要你来分析识别,并自行打桩,打桩参考如下方式
// 引用MOCKCPP的头文件
#include "mockcpp/mokc.h"
#include "mockcpp/mockcpp.h"
// 把FDSA_CommSendAckMsg打桩成固定返回FDSA_OK
MOCKER(FDSA_CommSendAckMsg).stubs().will(returnValue(FDSA_OK));
// 把FDSA_CommSendAckMsg打桩成FDSA_CommSendAckMsgStub
MOCKER(FDSA_CommSendAckMsg).stubs().will(invoke(FDSA_CommSendAckMsgStub));
```

### 增强版本(包含打桩策略)
```
请分析以下测试代码,识别需要打桩的接口并生成打桩代码:

<测试代码>

打桩要求:
1. 使用MOCKCPP进行打桩
2. 对于资源申请/释放函数,打桩为固定返回值
3. 对于异步接口,打桩为同步返回
4. 对于消息发送函数,打桩为成功返回
5. 保持打桩粒度合理,不要过度打桩

打桩策略:
- 资源申请函数:打桩为成功返回
- 资源释放函数:打桩为空操作
- 异步接口:打桩为同步完成
- 消息发送:打桩为成功返回
- 数据库操作:打桩为内存模拟

请生成完整的打桩代码,并说明每个桩函数的作用。
```

### 单用例生成
```

3. 给出修复方案

```

### 运行时错误调试
```
以下DT用例运行时失败:

<测试用例代码>
<错误输出>
<堆栈信息(如果有)>

1. 失败的可能原因
2. 打桩是否正确

- 不要修改检查结果来让测试通过

### CoreDump调试
```

<堆栈信息>

## 使用建议

1. **根据具体情况调整模板** - 这些模板是起点,需要根据具体模块和需求进行调整
2. **保持一致性** - 在同一个项目中使用相似的提示词风格
3. **迭代优化** - 根据实际效果不断优化提示词
4. **记录有效提示词** - 将有效的提示词记录下来,形成团队知识库
5. **结合实际代码** - 提示词应该包含具体的代码路径和模块信息

## 注意事项

1. **不要修改业务代码** - DT用例应该只测试,不应该修改被测代码
2. **打桩要合理** - 避免过度打桩导致测试失去意义
3. **检查点要明确** - 每个用例应该有清晰的验证点
4. **用例要可维护** - 避免过于复杂的测试逻辑
5. **保持简洁** - 提示词应该简洁明了,避免过于复杂
