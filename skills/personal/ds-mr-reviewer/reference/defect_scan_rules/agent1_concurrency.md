# 缺陷模式检测规则库 - Agent 1: 并发安全类

## 扫描范围与原则

- 聚焦于 MR diff 涉及的**被修改函数体**（不是全量扫描整个文件）
- 从 diff 中识别被修改函数名和位置，对被修改函数进行完整的函数体扫描
- 只报告有明确代码证据的问题
- 忽略 test/mock/stub/diagnose 代码
- 忽略 static inline 工具函数（调用者负责校验）
- 每条缺陷必须标注文件路径、行号、缺陷模式、严重度、根因、修复建议

---

## 1. 并发安全类（共5项）

### 1.1 并发竞态(非原子++/--)

**问题描述**: 多线程环境下对共享变量进行非原子的++或--操作，可能导致计数丢失或数据竞争。

**检测特征**:
- struct中定义的计数器成员变量
- 多线程回调函数中执行的++/--操作
- 无锁保护的共享变量访问

**检测关键词**: `++`, `--`, `completedCgNum`, `inFlightCgNum`, `count`, `num`

**误报排除**:
- 已有mutex/lock保护的操作
- atomic类型的变量
- static inline工具函数
- diagnose/diagnostic诊断代码

**严重度**: 严重

**修复建议**: 使用atomic_fetch_add/atomic_fetch_sub或加锁保护。

---

### 1.2 并发竞态(bool标志)

**问题描述**: bool类型变量作为多线程间共享的退出标志或控制标志时，非原子操作可能导致线程不可见。

**检测特征**:
- bool类型的退出标志或控制标志
- 多线程共享的标志变量
- 线程间通过flag通信

**检测关键词**: `bool`, `shouldExit`, `running`, `stopped`, `flag`

**误报排除**:
- static inline函数
- diagnose/diagnostic代码
- 可重入函数中的本地bool变量
- 已有atomic_bool声明的变量

**严重度**: 严重

**修复建议**: 使用atomic_bool或volatile bool，或使用互斥锁保护共享变量的读写。

---

### 1.3 并发竞态(共享变量)

**问题描述**: 多线程环境下对共享变量的读写缺乏同步保护，可能导致数据不一致。TOCTOU（Time-of-Check-to-Time-of-Use）是典型子模式：线程A检查条件后、使用前，线程B修改了条件状态。

**检测特征**:
- 全局或结构体级别的共享变量
- 多线程并发读写的变量
- 缺少同步机制的访问
- 检查与操作不原子(TOCTOU)
- 无锁队列check+act竞态

**检测关键词**: `global`, `static`, `shared`, `mutex`, `lock`, `ring`, `queue`, `bucket`, `list`, `TOCTOU`

**误报排除**:
- 线程局部存储(thread_local)
- 已有锁保护的操作
- 单线程上下文的变量

**严重度**: 严重

**修复建议**: 使用锁或原子操作保护共享变量的读写，消除检查与使用之间的时间窗口。

---

### 1.4 线程安全(锁未配对)

**问题描述**: 锁的获取和释放不匹配，可能导致死锁或锁泄漏。

**检测特征**:
- if分支中return后未Unlock
- 循环中锁获取后在异常路径未释放
- 多个函数共享锁但退出路径不一致

**检测关键词**: `MutexLock`, `MutexUnlock`, `lock`, `unlock`, `WdsMutex`

**误报排除**:
- goto cleanup模式的正确释放
- RAII自动锁
- 嵌套锁的正确配对

**严重度**: 严重

**修复建议**: 确保每个Lock都有对应的Unlock，使用RAII模式。

---

### 1.5 线程安全(锁顺序不一致/锁内阻塞)

**问题描述**: 多锁获取顺序不一致可能导致死锁；锁内有阻塞操作可能导致性能问题或死锁。

**检测特征**:
- 多个mutex按不同顺序获取
- 在锁内调用可能阻塞的函数
- 锁内执行IO操作

**检测关键词**: `MutexLock`, `lock`, `pthread_mutex`, `LockGuard`

**误报排除**:
- 单锁场景
- 递归锁
- 锁内只做轻量操作

**严重度**: 严重

**修复建议**: 统一多锁获取顺序；避免在锁内执行阻塞操作。
