# DT用例增强Skill使用指南

## 概述

这个skill专门用于对已有DT用例进行增强补齐,基于华为FDSA项目的实际经验总结而成。它采用思维链(CoT)方法,将复杂的增量用例开发分解为多个可管理的步骤。

## 适用场景

当你需要对已有DT用例进行增强补齐时,使用此skill:
- 对已有DT用例进行增强补齐
- 识别存量用例中遗漏的测试场景
- 补充增量DT测试用例
- 需要使用GTEST框架和MOCKCPP打桩的测试增强
- FDSA的Fusion或Dorado产品线的DT用例增强

## 快速开始

### 基本使用流程

1. **收集基本信息**: 收集4个关键路径 (模块代码目录、对外头文件目录、DT测试代码输出目录、存量DT用例目录)
2. **代码理解**: 理解代码结构,生成类图和接口文档
3. **全量场景用例设计**: 基于代码理解,设计所有可能的测试场景
4. **存量DT用例分析**: 分析存量DT用例,提取已覆盖的场景
5. **增量场景用例分析**: 对比分析,识别需要补充的场景,生成对比报告
6. **生成DT用例**: 生成增量DT用例代码
7. **编译和调试**: 编译并调试生成的用例

## 核心特性

### 1. 思维链(CoT)方法

将增量用例开发分解为7个步骤,避免在短记忆中保存过多细节:
- 收集基本信息
- 代码理解
- 全量场景用例设计
- 存量DT用例分析
- 增量场景用例分析 (含对比报告)
- 生成DT用例
- 编译和调试

### 2. 质量控制

每个步骤都有质量控制点:
- 代码理解: 检查接口、结构体、枚举是否准确
- 全量场景设计: 检查场景是否全面,接口是否正确
- 存量用例分析: 检查存量用例的场景提取是否准确
- 增量场景分析: 检查对比报告是否准确,覆盖理由是否充分
- 用例生成: 检查是否遵循三段式结构,是否只生成增量用例

### 3. 提示词模板

提供了丰富的提示词模板,涵盖所有步骤:
- 步骤0: 收集基本信息的提示词
- 步骤1: 代码理解的提示词
- 步骤2: 全量场景用例设计的提示词
- 步骤3: 存量DT用例分析的提示词
- 步骤4: 增量场景用例分析的提示词
- 步骤5: 生成DT用例的提示词
- 步骤6: 编译的提示词
- 步骤7: 用例执行和调试的提示词

### 4. 项目信息

包含完整的FDSA项目信息:
- 目录结构
- 测试框架
- 常用命令
- 打桩示例
- 最佳实践

### 5. 对比报告

提供详细的"已覆盖场景对比报告",包括:
- 全量场景统计
- 存量用例统计
- 场景覆盖对比表 (包含覆盖理由和证明)
- 需要补充的场景列表
- 总结和建议

## 使用技巧

### 1. 步骤化执行

不要一次性要求生成所有代码,应该分步骤执行:
1. 先让AI理解代码
2. 再确认全量场景
3. 分析存量用例
4. 对比分析,确认需要补充的场景
5. 最后生成具体代码

### 2. 人工审核

关键步骤需要人工审核:
- 代码理解阶段: 检查接口、结构体、枚举是否准确
- 全量场景设计阶段: 检查场景是否全面,接口是否正确
- 存量用例分析阶段: 检查存量用例的场景提取是否准确
- 增量场景分析阶段: 检查对比报告是否准确,覆盖理由是否充分

### 3. 迭代优化

如果生成的代码质量不高,可以:
1. 优化提示词
2. 分批生成用例 (一次不超过20个)
3. 提供更多上下文信息

### 4. 调试策略

推荐的调试策略:
1. 先编译通过整个DT框架
2. 再运行全量用例
3. 分析失败原因
4. 集中修复相同类型的问题

### 5. 验证对比报告

验证对比报告的准确性:
1. 检查覆盖理由是否合理
2. 检查证明信息是否充分
3. 检查是否有重复生成已有用例的情况
4. 检查是否有遗漏的场景

## 常见问题

### Q1: 如何避免重复生成已有用例?

A: 步骤4会生成"已覆盖场景对比报告",提供详细的覆盖理由和证明,确保不会重复生成。覆盖理由会详细说明存量用例的测试逻辑、输入参数、预期输出,解释为什么能覆盖目标场景。

### Q2: 对比报告中的覆盖理由如何生成?

A: AI会分析存量用例的测试逻辑、输入参数、预期输出,解释为什么能覆盖目标场景。参考 `references/comparison-report-example.md` 查看完整示例。

### Q3: 用例数量为什么限制为20个?

A: 增强场景通常用例数量较少,更小的粒度可以更精细地控制生成质量,避免上下文过大。

### Q4: 如何验证对比报告的准确性?

A: 人工审核对比报告,检查覆盖理由是否合理,证明是否充分。每个已覆盖场景都需要提供具体的存量用例名称、文件路径和行号。

### Q5: AI会偷懒,用例调试不通直接修改检查结果?

A: 提示词里明确不能修改检查结果,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

### Q6: AI会直接在业务代码中打桩?

A: 人工检查他修改的代码,并在提示词明确不允许修改业务代码,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

### Q7: 代码理解步骤出现大模型幻觉?

A: 详见步骤1中的提示词案例,强调与现存代码仓的头文件定义完全一致,必须提供完整路径和行号。

### Q8: AI自问自答,没有真正等待用户回复?

A: 在每个需要用户确认的地方,使用明确的停止指令。使用"请回复"或"请确认"这样的明确指令。绝不能在用户回复之前继续任何操作。

### Q9: AI自动跳到下一步,没有等待用户确认?

A: 这是最严重的问题,必须严格避免。必须在每个步骤完成后明确等待用户回复"确认"或类似的确认信息。必须使用明确的停止指令。

## 最佳实践

### 1. 一次只做一件事

不要让AI同时做多个任务:
- 先让AI把编译调过
- 然后用例以测试套为粒度进行调试
- 逐步解决问题

### 2. 提供准确的上下文

给AI提供准确的代码路径和模块信息:
- 明确代码路径
- 明确模块名称
- 明确依赖关系
- 明确测试框架

### 3. 人工介入关键步骤

在关键步骤人工介入:
- 审核代码理解结果
- 审核全量场景设计结果
- 审核存量用例分析结果
- 审核对比报告
- 定位复杂问题

### 4. 保持提示词简洁

提示词应该:
- 简洁明了
- 避免冗长
- 重点突出
- 结构清晰

### 5. 记录有效提示词

将有效的提示词记录下来:
- 形成团队知识库
- 方便后续复用
- 持续优化改进

### 6. 验证对比报告

验证对比报告的准确性:
- 检查覆盖理由是否合理
- 检查证明信息是否充分
- 检查是否有重复生成已有用例的情况
- 检查是否有遗漏的场景
