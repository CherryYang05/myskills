# DT用例生成Skill

这是一个专门为华为FDSA项目设计的DT(动态测试)用例生成skill,采用思维链(CoT)方法将复杂的DT用例开发分解为多个可管理的步骤。

## 适用场景

- 生成DT测试用例
- 为大颗粒特性(2w行代码规模)开发测试用例
- 需要使用GTEST框架和MOCKCPP打桩的测试开发

## 核心原则

### 1. 指令优于约束
明确指定期望操作比罗列禁止事项效果更好。构建提示时应直接引导模型。

### 2. 实验与迭代
提示工程是一个迭代过程,从初步设计开始,进行测试,分析输出,识别不足,然后优化提示。

### 3. 分解复杂任务
对于大颗粒特性,采用思维链(CoT)形式把DT生成拆分成多个步骤,避免在短记忆中保存过多细节。

### 4. **真正的交互式确认(最重要原则)**
**这是绝对不能违反的原则**:
- 每次询问用户问题后,必须**真正停下来等待用户回复**
- **绝不能自问自答**
- **绝不能自动假设用户的答案**
- **绝不能在用户回复之前继续下一步**
- **每一步都使用subagent的方式执行，减少上下文干扰**
- 必须看到用户明确的回复后才能继续

### 5. **明确的停止指令**
**在每个需要用户确认的地方,使用以下明确的停止指令**:
```
请回答以上问题,我会等待你的回复,不会自动继续。
```
或者:
```
请确认以上信息,回复"继续"或"确认"后我会进行下一步。
```

## DT用例生成流程

### **最重要规则: 每一步完成后必须真正等待用户回复,绝不能自问自答**

### 步骤0: 收集基本信息

在开始之前,必须先收集以下信息:

**必须询问用户的3个问题:**
1. 模块的代码目录在哪里?(绝对路径或相对路径)
2. 对外头文件目录在哪里?(绝对路径或相对路径)
3. DT测试代码的输出目录在哪里?(绝对路径或相对路径)

**操作流程:**
1. 向用户提出上述3个问题
2. **重要**: 必须明确告诉用户需要回答这些问题
3. **重要**: 必须明确表示会等待用户回复
4. **重要**: 绝不能自问自答,绝不能假设任何答案
5. 等待用户回答所有问题
6. 确认信息无误后,进入步骤1

**正确的对话示例:**
```

- **标准UML类图**(使用PlantUML或Mermaid格式)
- 关键结构体(包含完整路径和行号)
- 关键对外接口(包含完整路径和行号)
- 需要打桩的接口(包含代码中使用位置)

## 常见问题和解决方案

### 问题1: AI会偷懒,用例调试不通直接修改检查结果
**解决办法:** 提示词里明确不能修改检查结果,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

### 问题2: AI会直接在业务代码中打桩,当是DT运行时,修改返回结果
**解决办法:** 人工检查他修改的代码,并在提示词明确不允许修改业务代码,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

### 问题3: 代码理解步骤出现大模型幻觉
**解决办法:** 详见步骤1中的提示词案例,强调与现存代码仓的头文件定义完全一致,必须提供完整路径和行号。

### 问题4: AI自问自答,没有真正等待用户回复
**解决办法:**
- 在每个需要用户确认的地方,使用明确的停止指令
- 使用"请回复"或"请确认"这样的明确指令
- 绝不能在用户回复之前继续任何操作
- 绝不能假设用户的答案

### 问题5: AI自动跳到下一步,没有等待用户确认
**解决办法:**
- 这是最严重的问题,必须严格避免
- 必须在每个步骤完成后明确等待用户回复"确认"或类似的确认信息
- 必须使用明确的停止指令

### 问题6: 代码分析文档信息不够详细
**解决办法:**
- 必须要求AI提供完整路径和行号
- 必须要求AI验证所有接口、结构体、枚举在代码中真实存在
- 必须要求AI提供打桩接口的代码中使用位置
- 不能只提供接口名称,必须提供详细信息

## 最佳实践

1. **一次只让AI干一件具体的事情**,比如,先让AI把编译调过,然后用例以测试套为粒度进行调试。

2. **当AI自己无法完成任务时,人工定位,并把原因告诉AI**,让AI来修改,这样后面其它的用例他能能快速解决。

3. **CoreDump类问题,先人工找到堆栈,然后把堆栈给AI**,这样速度更快。

4. **每一步都要真正等待用户确认,绝不能自问自答**,这是最重要的交互原则。

5. **提供示例:** 提供one-shot或few-shot示例是最有效的模型引导方法之一。

6. **设计简洁:** 保持提示简明、清晰且易于理解。避免不必要的专业术语或过度复杂措辞。

7. **明确输出要求:** 清晰定义模型响应的期望格式、长度、风格和内容。

8. **控制最大Token长度:** 使用模型配置或明确提示指令管理生成输出的长度。

9. **提示中使用变量:** 对应用中使用的提示,采用变量使其动态可复用,避免硬编码特定值。

10. **尝试输入格式与写作风格:** 试验不同提示措辞方式(疑问、陈述、指令)并探索不同语气或风格,以寻找最佳效果。

11. **要求提供详细信息:** 必须要求AI提供完整路径、行号、使用位置等详细信息,不能只提供名称。
