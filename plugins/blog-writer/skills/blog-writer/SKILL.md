# Tech Blog Writer

将学习对话、笔记与实践记录整理成可长期保存和公开发布的中文博客。题材跟随当前素材，可写知识解析、实操教程和经验复盘。

从对话中提取问题、证据、推理过程和结论，按读者理解所需的顺序重组。文章应在脱离原始对话后也能独立阅读。

文章应具有以下特征：

- 技术事实准确；
- 逻辑链完整；
- 信息密度高；
- 语言克制、自然；
- 结构服务于内容，而不是套固定模板；
- 不保留明显的聊天痕迹；
- 不使用典型 AI 生成文章的口吻和排版习惯。

---

# 一、工作流程

用户在学习对话末尾说“把这段整理成博客”时，默认使用当前对话中可见且与主题有关的内容。只有用户要求时才交付素材表或交接稿。用户给的是现成文章且只要求审稿时，按第十五节审校并按第十四节确定编辑范围。

1. 确定读者、核心问题和文章类型。
2. 提取素材并设计结构。满足大纲确认条件时先确认。
3. 撰写 Markdown。按第十七节使用智能图并把 HTML 写进正文。
4. 从读者角度审查、修订、回查证据和检查交付文件。

流程本身应严格执行，但正文结构不应机械套模板。

---

# 二、直接成稿与大纲模式

主题、读者和主要证据明确时，默认在同一轮完成取材、起稿、读者审稿和文件交付。用户说“快速出一篇”“直接写”或“不用确认”时，以能核实的范围直接成稿。

用户明确要求先看大纲，或读者、拆篇、关键事实的不同选择会实质改变主线时，先给第 4.4 节所述的大纲再继续。能从已有素材合理确定范围时，直接推进。若只缺一项决定结论的证据，先找具体证据或缩小结论范围。

---

# 三、阶段 1：确定文章类型

以读者需要为准，根据素材判断：

- **教程 / How-to**。读者要完成具体操作。围绕环境、配置、步骤、验证和失败处理组织。
- **知识解析**。读者要理解为什么。围绕必要前置概念、机制、推理、算例和适用条件组织。
- **复盘 / 经验**。读者要理解某项判断如何形成。保留有据可查的时间线、改变判断的证据、决策和结果。

用户指定类型时采用该类型。类型明确时直接进入取材。一篇文章可以有多种素材，主线根据读者要完成的事确定。

---

# 四、阶段 2：素材提取与大纲确认

## 4.1 提取内容

按用户最新明确的范围阅读当前素材，优先定位用户的实际追问和后来被确认的纠正。短对话先快速过一遍再起稿。长对话或混合主题按子问题切段，合并重复结论，保留能解释判断变化的追问。若无法访问的片段会改变主结论，只索取那段材料，或缩小成文范围。

在内部形成简短素材表。短稿可只记必要条目，长稿为关键陈述保留消息轮次、文件章节或来源链接，便于审稿时回查。

| 素材 | 保留内容 | 处理方式 |
| --- | --- | --- |
| 原始问题与约束 | 读者要解决的问题、环境、前提、适用条件 | 放在读者需要它们的地方 |
| 认知转折 | 被反例推翻的理解、导致下一步改变的失败或取舍 | 交代错误为何出现，紧接着给纠正或证据 |
| 可核验证据 | 最小算例、原始来源、版本、关键命令与实际输出 | 最能支撑结论的证据放进正文 |
| 未验证或私有素材 | 讨论中的推测、撤回的数字、内部资料 | 私有素材留在取材记录。必要的假设在结论旁清楚标明 |

然后提取以下内容。

### 核心问题

文章究竟试图回答什么问题。

应尽量归纳为一个明确的问题，而不是一组松散主题。

### 必要背景

理解问题所需的上下文，包括：

- 技术环境；
- 已有方案；
- 前置概念；
- 问题产生的原因。

只保留理解正文真正需要的背景。

### 关键知识

提取对话中已经明确讨论过的：

- 原理；
- 数据结构；
- 算法；
- 系统机制；
- API；
- 命令；
- 配置；
- 代码；
- 数学推导。

### 推理链

重点保留：

> 为什么出现问题 → 为什么直觉方案不成立 → 真正的约束是什么 → 最终如何理解或解决。

这是文章最重要的内容之一。

不要只保留最终结论。

### 容易误解的地方

记录对话中实际出现过的：

- 概念混淆；
- 错误理解；
- 不严谨说法；
- 报错；
- 反例；
- 边界条件。

这些内容通常比单纯的“正确答案”更有文章价值。

### 最终结论

提取能够长期复用的知识。说清哪些结论仅在当前设定成立，以及哪个条件改变后需要重新判断。

---

## 4.2 控制文章范围

一篇文章原则上只处理一个核心主题。

如果对话中出现多个可以独立成文的主题：

- 保留与主问题直接相关的内容；
- 次要内容可以简短提及；
- 明显独立的内容不要强行塞入同一篇文章。

文章宁可短而完整。用一句话写下目标读者读完能理解、判断或复现什么。给每一节关联一个读者问题和一项支撑它的证据。

例如，聊天先误以为排序结果的键相同就满足稳定性，后来用 `[(2,A),(1,X),(2,B)]` 发现两种有序输出的 A、B 顺序不同。写作时先用带身份标签的算例定义稳定性，再解释插入排序遇到同键时的停止条件。已撤回的性能数字不进入正文，另外讨论的日志分类留作单独主题。

---

## 4.3 补充历史上下文

如果当前讨论明确依赖此前对话，例如：

- “上次提到的 Paxos 流程”
- “之前分析过这个模块”
- “沿用前面的设计”

优先使用用户给的原对话链接、导出或交接稿，只补读与主线有关且当前可访问的部分。使用旧素材时，在素材表或需要展示的大纲中注明它补足的证据。

不要悄悄混入与当前文章无关的个人背景或其他讨论。

---

## 4.4 输出文章大纲

需要对外展示大纲时，应简洁且能看出完整逻辑。明确各节解决的读者问题，以及关键算例、实验或来源。

推荐格式：

```text
文章大纲

标题：
类型：

文章要回答的问题：
[一句话]

结构：

1. [章节名称]
   [这一节解决什么问题]

2. [章节名称]
   [这一节解决什么问题]

3. [章节名称]
   [这一节解决什么问题]

...

关键示例：
- [代码 / 命令 / 数学推导 / 图示]

计划保留的踩坑或误解：
- [...]

不会纳入正文的内容：
- [...]
```

不要为了显得完整而人为制造很多章节。

一般情况下：

- 短文章 3～5 个主要章节；
- 深度文章 5～8 个主要章节；

已经足够。

---

## 4.5 大纲确认规则

仅在第二节规定的大纲模式下等待确认。用户说“可以”“就这样”或“开始写”即可继续。若回复提出实质性的结构修改且未要求直接成稿，先按反馈更新大纲。标题或局部表达的反馈可在正文中直接处理。

---

# 五、阶段 3：正文生成

根据内部结构或已经确认的大纲写成完整 Markdown。按第十七节处理适合可视化的段落，并在第十五节的审稿中检查图文是否一致。

用户提供或明确认可同类文章时，可参考一两篇，观察作者的叙述视角、段落密度和术语用法。保留有依据的个人判断，不补写个人经历。正文默认作为 Markdown 文件交付，用户明确要求在聊天中查看时也可直接展示。

---

# 六、文章写作原则

这是本技能最重要的一部分。

## 6.1 写成文章，而不是整理聊天记录

禁止出现类似：

- “前面提到”
- “刚才讨论了”
- “这里再解释一下”
- “用户一开始认为”
- “后来发现”
- “我们之前说过”

除非文章本身就是故障复盘或实验记录。

聊天中的问答顺序可以被完全打散。

文章应按照知识本身的逻辑重新组织。

---

## 6.2 接近技术书籍，而不是 AI 博客模板

正文应具有连续的论述感。

优先采用：

> 问题 → 条件 → 推理 → 结果

而不是：

> 金句 → 列表 → 金句 → 列表 → 总结金句。

避免为了“易读”把每一句话都拆成单独段落。

一个自然段应承担一个完整的论述单元。

如果三四句话本来属于一个逻辑整体，应放在同一个段落里。

---

## 6.3 不制造虚假的戏剧性

避免：

- “真正精彩的地方来了”
- “这里隐藏着一个巨大的坑”
- “最神奇的是”
- “这才是问题的本质”
- “答案其实非常简单”
- “事情开始变得有意思”
- “看到这里可能会震惊”

如果某个结论重要，直接解释它为什么重要。

---

## 6.4 少用口号式总结

避免频繁出现：

```text
一句话总结：

本质上：

真正需要记住的是：

核心思想：

最关键的一点：
```

这些表达偶尔可以使用，但不能作为每个章节的固定结尾。

尤其不要把已经解释过的内容再次换一种说法重复一遍。

---

## 6.5 小标题应描述内容

推荐：

```text
## 第一名出现在第 k 个位置时的成功概率

## 从有限候选人推广到连续近似

## 1/e 是如何得到的

## 这个模型依赖哪些假设
```

避免：

```text
## 一个神奇的结果

## 真正的问题来了

## 更进一步

## 最重要的一点

## 终极总结
```

标题应该能够直接进入目录，并告诉读者这一节是什么。

---

## 6.6 不滥用粗体

粗体只用于：

- 首次出现的重要概念；
- 极少量需要强调的约束；
- 定义中的关键词。

不要一段中出现多个粗体句。

禁止使用粗体代替正常论证。

---

## 6.7 不滥用引用块

`>` 只用于：

- 引用原始定义；
- 提炼一个确实值得单独呈现的结论；
- 注意事项。

不要每章开头都使用 blockquote。

文章开头也不强制要求“核心结论”引用块。

如果正文自然开篇更合适，直接进入背景即可。

---

## 6.8 列表只在存在并列关系时使用

适合列表的内容：

- 条件；
- 参数；
- 步骤；
- 对比项；
- 独立的边界情况。

不适合列表的内容：

连续的因果推理。

如果内容是：

> A 导致 B，B 又导致 C，因此得到 D

应写成段落，而不是拆成四个 bullet。

---

# 七、技术深度解析文章

技术解析的重点是建立完整的因果关系。

常见组织方式如下，但不是固定模板：

```text
# 标题

## 问题背景

为什么会出现这个问题。

## 模型 / 架构 / 关键概念

先建立读者理解后文所需的抽象。

## 核心机制

解释系统或算法如何工作。

## 推导或执行过程

沿数据流、控制流、状态变化或数学关系逐步分析。

## 容易误解的地方

解释反直觉点和边界条件。

## 适用范围

说明模型成立的前提，以及现实中哪些假设可能不成立。

## 总结
```

实际章节名称应根据主题重新设计。对话里真实出现的混淆，优先用同一个算例或反例讲清。先交代直觉在哪个条件下会出错，再给出可复算的结果。无需为了补齐模板另造场景。

延伸内容以一项能加深当前理解的内容为主，例如结论失效的边界、实现中的一个变体，或有根据的延伸阅读。说明它与本文问题的关系。来源或验证不足时先保留正文主线。

---

# 八、教程文章

教程以可复现为第一目标。

常见结构：

```text
# 标题

## 背景与目标

## 环境与前提

## 实现步骤

## 关键机制说明

## 常见问题

## 验证结果

## 总结
```

具体结构根据任务复杂度调整。开头明确目标产物与环境、版本、权限和依赖。区分必须配置和可选设置，解释占位符该替换成什么。用最少步骤先走通一次，再补必要的配置变化和故障处理。

每个关键操作步骤包含以下要素。

1. 要执行的命令或代码；
2. 为什么这样做；
3. 关键参数的意义；
4. 正常情况下会得到什么结果。

只解释会影响选择和结果的参数。关键步骤给出可观察的成功信号，例如具体输出、文件内容或界面状态。故障段落交代症状、定位依据、修复和必要的恢复步骤。执行过的步骤注明验证环境，依文档整理的步骤如实区分。

# 九、代码与命令

代码只保留理解问题所必需的部分。

优先展示最小但完整的示例。

代码块必须注明语言：

````markdown
```python
...
```

```bash
...
```

```c
...
```

```yaml
...
```
````

如果代码来自真实项目，并且文件路径对于理解上下文有价值，可以写：

```text
src/runtime/executor.py
```

然后再展示代码。

不要伪造原始项目中不存在的函数、日志和配置。

如果为了说明原理必须写简化示例，应明确说明：

> 以下代码为简化示意。

# 十、数学与 TeX 公式规范

文章需要兼容 Halo 当前的 Markdown 数学渲染。

## 10.1 行内公式

所有行内数学表达式使用：

```markdown
$x = \frac{1}{e}$
```

禁止使用：

```text
\( ... \)
```

---

## 10.2 块级公式

所有独立公式必须使用：

```markdown
$$
P(r)
=
\frac{r}{n}
\sum_{k=r+1}^{n}
\frac{1}{k-1}
$$
```

禁止使用：

```text
\[ ... \]
```

禁止混用多种公式定界符。

全文统一：

```text
行内：$...$
块级：$$...$$
```

---

## 10.3 公式排版

较短的公式优先放在行内，例如：

```markdown
最优观察比例为 $1/e$。
```

只有以下情况使用块级公式：

- 推导过程；
- 多项等式；
- 需要单独强调的重要公式；
- 较长的表达式。

不要把每一个变量都单独放成一个块级公式。

例如不推荐：

```markdown
假设：

$$
n
$$

表示候选人数。
```

应写成：

```markdown
设候选人数为 $n$。
```

这条规则非常重要。

大量无必要的块级公式会让文章产生明显的机器生成感。

---

## 10.4 TeX 命令

公式内部可以正常使用：

```tex
\frac{}{}
\sum
\int
\ln
\approx
\cdot
\mid
\text{}
\boxed{}
```

但应避免为了排版效果使用 Halo/KaTeX 可能不支持的冷门宏。

# 十一、语言规范

## 11.1 中文与英文术语

正文使用中文。

技术术语保留通行英文名称，例如：

- Paxos
- WAL
- checkpoint
- rollback
- cache
- Secretary Problem
- Optimal Stopping

术语第一次出现时，可以补充中文解释：

> Optimal Stopping（最优停止）

之后直接使用英文或业内最常见写法。

不要反复中英文并列。

---

## 11.2 中文标点

中文句子使用全角中文标点：

```text
，。；：？！“”
```

代码、命令、路径、数学公式和英文标识符内部保持原始字符。

例如：

```text
执行 `git reset --mixed HEAD~1` 后，工作区文件不会被删除。
```

---

## 11.3 避免第二人称

技术文章默认面向不特定读者。

避免：

- “你需要……”
- “你会看到……”
- “如果你……”
- “我们来看……”
- “让我们……”

推荐：

- “需要先……”
- “此时会输出……”
- “若……则……”
- “下面分析……”
- “可以得到……”

但也不要为了完全回避主语而写出生硬的公文语句。

自然性优先。

---

## 11.4 不使用 AI 自我表述

正文不得出现：

- “作为 AI”
- “这里我认为”
- “我来解释”
- “下面我会”
- “为了帮助理解”

文章作者不应在正文中解释自己的生成过程。

---

# 十二、信息边界

所有技术事实应满足以下至少一个条件：

1. 来自当前对话中有证据支持的结论。聊天里的解释、猜测与后续被纠正的说法需回查素材。
2. 来自用户提供的代码或资料；
3. 来自明确检索并验证过的外部资料；
4. 属于解释当前知识所必需且稳定的基础知识。

不要为了让文章显得丰富而自行添加：

- 未验证性能数据；
- 不存在的源码实现；
- 未讨论过的工程经验；
- 虚构故障案例；
- 不确定的历史事实。

如果事实存在不确定性，应明确写出条件或限制。实测、公开文档和教学示例分开。结论依赖自设参数、测试环境、版本或特殊口径时，把条件紧挨结论写。公开稿仅纳入可公开资料。

---

# 十三、总结章节

总结的目标是压缩整篇文章的逻辑，而不是重复目录。

通常使用 2～4 个自然段即可。

可以包含：

- 这个问题最终如何理解；
- 最重要的机制；
- 哪些假设决定了结论的适用范围；
- 在实际工程中真正值得保留的思想。

不强制使用：

- “普通写法 vs 新方案”
- 对比表
- checklist
- 金句
- boxed conclusion

只有内容本身适合时才使用。

最后一句应自然结束全文，不必刻意制造“升华”。

# 十四、迭代修改

文件生成后，如果用户要求修改：

### 局部修改

例如：

- 改标题；
- 修改某段表述；
- 增加一个例子；
- 删除某节；

优先进行局部编辑，不重新生成全文。

### 结构修改

例如：

- 重组章节；
- 合并两节；
- 改变文章主线；

先给出简短结构方案，按用户的确认或直接修改指令执行。

# 十五、最终质量检查

生成完成后，从第一次接触这个主题的目标读者视角重新阅读全文，按以下顺序审校。

1. 只读成稿。找出缺少定义、推理跳步、图文冲突或教程无法复现的具体位置，直接修改。检查开头是否交代问题，以及标题承诺是否在正文兑现。
2. 再做语言编辑。删除重复、套话和碎片化排版。保留作者的语气、观点、技术限定和不确定性。
3. 回看素材和最终文件。核对数据、来源、公式、命令、版本、链接和图。确认正文里出现了最能支撑主结论的证据。实际未运行的操作按文档或示例注明。

以下清单用于复核。

### 知识完整性

- 是否存在没有解释就使用的关键概念？
- 因果关系是否完整？
- 结论是否能够从前文推出？

### 技术准确性

- 代码是否与讨论一致？
- 数学公式是否正确？
- 示例是否真的支持结论？
- 是否遗漏重要前提？

### 文章性

- 是否像文章，而不是聊天记录？
- 是否存在大量碎片化短段？
- 是否重复同一个结论？
- 是否存在明显模板痕迹？
- 章节是否过度细分？
- bullet 是否过多？
- 是否存在不必要的“总结式金句”？

### 外部读者可读性

- 离开原始对话后是否仍然能够理解？
- 标题和目录是否能准确描述内容？
- 示例是否有足够上下文？
- 首次出现的专业术语是否得到解释？

### Halo Markdown

必须检查：

- 行内公式全部为 `$...$`；
- 块级公式全部为 `$$...$$`；
- 不存在 `\(...\)`；
- 不存在 `\[...\]`；
- 不要把简单变量单独写成块级公式。

发现问题时直接修正，不需要向用户展示内部 checklist。

# 十六、文件交付

文件名格式：

```text
YYYY-MM-DD-[slug].md
```

例如：

```text
2026-04-05-wsl2-docker-proxy-setup.md
2026-04-05-ccdb-paxos-log-deletion.md
2026-08-20-secretary-problem-37-percent-rule.md
```

`slug` 使用简洁的小写英文单词，以连字符连接。

文件保存到当前环境可供用户下载的输出位置。

最终回复只需要：

1. 简短说明文章已经完成；
2. 文件下载链接；
3. 如果进行了值得说明的修正，用一句话说明。

默认提供文件链接。用户要求在聊天中查看全文时按其要求展示。

要求传到 Halo 时，用当前环境可用的发布连接查询站点已有分类和标签。优先复用匹配项，缺项列为建议。按稳定的文章别名或已记录的文章 ID 检查是否已有对应稿件，避免重复创建。存为草稿后回读正文、分类标签和发布状态，并检查主题预览。有明确的公开发布指令时再发布该稿，核对公开链接。缺少连接时交付成稿和建议的分类标签。

# 十七、智能图与 Markdown 内嵌 HTML

在起草结构时选出读者会停下来想象的步骤、关系或变化。优先画清最容易混淆的那一点。静态关系适合对照、流程或结构图，变量变化和多状态过程适合交互。图回答一个具体问题，并使用正文同一组输入、标签和单位。纯文字更清楚时可省略，用户要求配图时至少做一张解释主线的图。

1. **在 ChatGPT 预览。** 在当前会话具备可视化能力且交付场景适用时，优先用 Intelligent UI 或交互式可视化预览。已有图就复用其数据、标签、默认状态和阅读顺序。有 HTML 源码时转成正文片段，只有预览时用同一数据重建 HTML。缺少预览能力时仍完成 Markdown 内嵌图。
2. **写进最终 Markdown。** 在对应段落附近直接写原始 HTML 标签，片段前后留空行。图片链接、独立附件、聊天组件、Mermaid 和带围栏的 HTML 代码块均不能替代正文里的图。图中展示关键值、单位和标签，给箭头和颜色明确的语义。
3. **按目标渲染。** Halo/ByteMD 优先用 `div`、`p`、`span`、`strong` 或语义表格，以少量内联 `style` 做间距、边框和自适应。继承主题文字颜色，关键关系用文字标出。正文避免 `script`、`iframe`、`style` 标签、原始 SVG、事件属性和外部运行依赖。其他标签或样式按实际编辑器预览确认。
4. **保留交互价值。** 如果预览需要滑块、切换或动画，正文内嵌能独立说明问题的默认状态或关键步骤。可补一份无外部依赖的独立 HTML 交互版。有公开托管地址时先验证再链接。

以下是原始 HTML 片段的示意，交付时去掉围栏。示例中箭头与两侧的文字共同表达转换关系。

```html
<div style="display:flex;flex-wrap:wrap;gap:0.5rem;align-items:center">
  <div style="padding:0.5rem;border:1px solid currentColor"><strong>输入</strong> · 原始数据</div>
  <span>→</span>
  <div style="padding:0.5rem;border:1px solid currentColor"><strong>输出</strong> · 转换结果</div>
</div>
```

## 出稿前检查图

- 箭头的方向和连接对象与正文一致。涉及多状态时，首帧也能说明问题，计算图核对默认值、边界输入、单位和公式。
- 图在窄屏会换行，文字与对比在主题切换后仍清晰。关键关系可由文字理解。
- 查看最终 `.md` 源文件，确认图标签在正文中，前后有空行，未被围栏或缩进变成代码。HTML 片段内部避免用空行切断同一块。
- 按目标渲染器检查。Halo 草稿可用时，打开实际主题预览。展示交互依赖当前客户端能力，静态 HTML 仍须能独立读懂。
