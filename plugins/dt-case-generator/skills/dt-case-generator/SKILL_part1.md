# DT用例生成Skill

这是一个专门为华为FDSA项目设计的DT(动态测试)用例生成skill,采用思维链(CoT)方法将复杂的DT用例开发分解为多个可管理的步骤。

## 适用场景

- 为FDSA项目生成DT测试用例
- 为大颗粒特性(2w行代码规模)开发测试用例
- 需要使用GTEST框架和MOCKCPP打桩的测试开发
- FDSA的Fusion或Dorado产品线的DT用例开发

## 核心原则

### 1. 指令优于约束
明确指定期望操作比罗列禁止事项效果更好。构建提示时应直接引导模型。

### 2. 实验与迭代
提示工程是一个迭代过程,从初步设计开始,进行测试,分析输出,识别不足,然后优化提示。

### 3. 分解复杂任务
对于大颗粒特性,采用思维链(CoT)形式把DT生成拆分成多个步骤,避免在短记忆中保存过多细节。

### 4. **真正的交互式确认(最重要原则)**
**这是绝对不能违反的原则**:
- 每次询问用户问题后,必须**真正停下来等待用户回复**
- **绝不能自问自答**
- **绝不能自动假设用户的答案**
- **绝不能在用户回复之前继续下一步**
- 必须看到用户明确的回复后才能继续

### 5. **明确的停止指令**
**在每个需要用户确认的地方,使用以下明确的停止指令**:
```
请回答以上问题,我会等待你的回复,不会自动继续。
```
或者:
```
请确认以上信息,回复"继续"或"确认"后我会进行下一步。
```

## DT用例生成流程

### **最重要规则: 每一步完成后必须真正等待用户回复,绝不能自问自答**

### 步骤0: 收集基本信息

在开始之前,必须先收集以下信息:

**必须询问用户的3个问题:**
1. 模块的代码目录在哪里?(绝对路径或相对路径)
2. 对外头文件目录在哪里?(绝对路径或相对路径)
3. DT测试代码的输出目录在哪里?(绝对路径或相对路径)

**操作流程:**
1. 向用户提出上述3个问题
2. **重要**: 必须明确告诉用户需要回答这些问题
3. **重要**: 必须明确表示会等待用户回复
4. **重要**: 绝不能自问自答,绝不能假设任何答案
5. 等待用户回答所有问题
6. 确认信息无误后,进入步骤1

**正确的对话示例:**
```
你: 我需要为link_subhealth模块生成DT用例
我: 好的,为了生成高质量的DT用例,我需要先了解3个基本信息,请你回答:

1. 模块的代码目录在哪里?(例如: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth)
2. 对外头文件目录在哪里?(例如: fusion/product/taishan_src/fdsa/include)
3. DT测试代码的输出目录在哪里?(例如: fusion/product/test/fdsa/fdsa_dt_linux/dt_src/link_subhealth)

**请回答以上3个问题,我会等待你的回复,不会自动继续。**

(这里必须停下来,等待用户回复)
```

**错误的对话示例(绝不能这样做):**
```
你: 我需要为link_subhealth模块生成DT用例
我: 好的,我假设模块代码目录是fusion/product/taishan_src/fdsa/src/plugins/link_subhealth...

(错误:自问自答,没有等待用户回复)
```

### 步骤1: 代码理解

首先需要让CodeAgent准确理解代码的结构,包括:
- UML类图
- 关键结构体(包含完整路径和行号)
- 关键对外接口(包含完整路径和行号)
- 需要打桩的接口(包含代码中使用位置)

**提示词模板:**
```
请帮我理解以下模块的代码:

模块代码目录: <模块代码目录>
对外头文件目录: <对外头文件目录>

请按照以下要求生成代码分析文档,保存到 <输出文件名>.md:

1. 生成准确的UML类图,使用标准的UML图表示

2. 识别所有关键结构体,对每个结构体包含:
   - 结构体名称
   - 完整定义路径(绝对路径)
   - 定义所在的行号
   - 所有字段的名称和类型
   - 结构体的大小(如果是C结构体)
   - 在代码中的使用情况

3. 识别所有关键枚举,对每个枚举包含:
   - 枚举名称
   - 完整定义路径(绝对路径)
   - 定义所在的行号
   - 所有枚举值及其含义

4. 识别所有对外接口(函数),对每个接口包含:
   - 函数名称
   - 完整定义路径(绝对路径)
   - 定义所在的行号(函数声明行号)
   - 返回值类型
   - 所有参数的名称和类型
   - 函数功能描述
   - 在代码中的调用情况(至少提供2个调用位置,包含完整路径和行号)

5. 识别需要打桩的接口,对每个需要打桩的接口包含:
   - 接口名称
   - 完整定义路径(绝对路径)
   - 定义所在的行号
   - 打桩原因(为什么需要打桩)
   - 在代码中的具体使用位置(至少提供2个调用位置,包含完整路径、文件名和行号)
   - 推荐的打桩方式(固定返回值、调用桩函数等)

6. **重要**: 必须验证所有接口、结构体、枚举都在代码中真实存在且定义一致
   - 对每个接口,验证其声明和实现是否匹配
   - 对每个结构体,验证其字段是否正确
   - 对每个枚举,验证其枚举值是否正确
   - 如果发现不一致,必须在文档中明确指出

7. **重要**: 所有路径必须是绝对路径或相对于项目根目录的完整路径
   - 不能只写文件名,必须包含完整路径
   - 例如: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth/common/fdsa_link_subhealth_cfg_base.h:19

8. 生成目录结构,包含所有相关文件

9. 总结模块的主要功能和依赖关系

请确保文档中的所有信息都经过验证,与实际代码完全一致。
```

**操作流程:**
1. 使用用户提供的代码路径生成代码分析文档
2. 生成完成后,展示关键信息给用户
3. 要求用户检查以下内容:
   - 所有接口、结构体、枚举是否在代码中真实存在
   - 路径和行号是否准确
   - 打桩接口的识别是否合理
   - 信息是否详细完整
4. **重要**: 明确告诉用户需要确认
5. **重要**: 明确表示会等待用户回复
6. **重要**: 绝不能自动进入步骤2
7. 等待用户确认或修改意见
8. 如果用户发现问题,根据反馈修改
9. 只有在用户明确确认后,才能进入步骤2

**正确的对话示例:**
```
我: 我已经完成了link_subhealth模块的代码分析,生成了link_subhealth_analysis.md文档。

关键信息:
- 共识别出XX个对外接口,每个接口都包含完整路径和行号
- 共识别出XX个结构体,每个结构体都包含完整路径和行号
- 共识别出XX个枚举,每个枚举都包含完整路径和行号
- 共识别出XX个需要打桩的接口,每个接口都包含代码中使用位置

示例信息:
- 接口 FdsaLinkSubhealthCfgInit
  - 定义路径: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth/master/fdsa_link_subhealth_cfg_master.h:19
  - 返回值: int32_t
  - 参数: void
  - 功能: 初始化链路亚健康配置

- 结构体 LINK_SUBHEALTH_CFG_INFO
  - 定义路径: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth/common/fdsa_link_subhealth_cfg_base.h:60
  - 字段: value (uint32_t), name[64] (char)

- 需要打桩的接口 fdsaLogError
  - 定义路径: (外部接口)
  - 使用位置1: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth/common/fdsa_link_subhealth_cfg_base.c:18
  - 使用位置2: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth/common/fdsa_link_subhealth_cfg_base.c:23
  - 打桩原因: 日志接口,DT中不需要真实日志输出
  - 推荐打桩方式: 固定返回,空操作

请检查以下内容:
1. 所有接口、结构体、枚举是否在代码中真实存在?
2. 路径和行号是否准确?
3. 打桩接口的识别是否合理?
4. 信息是否详细完整?

**请确认以上信息,回复"继续"或"确认"后我会进行下一步。如果发现问题,请告诉我需要修改的地方。**

(这里必须停下来,等待用户回复)
```

**错误的对话示例(绝不能这样做):**
```
我: 我已经完成了代码分析,生成了link_subhealth_analysis.md文档。

关键信息:
- 共识别出XX个对外接口
- 主要接口包括: FdsaLinkSubhealthCfgInit, FdsaLinkSubhealthGetSwitch等

现在进入步骤2,分析用例场景...

(错误:没有提供详细路径和行号,没有等待用户确认,直接进入下一步)
```

**注意:** 这一步是减少后续AI产生幻觉的关键,业务专家必须重点审核。

如果出现幻觉(生成代码中不存在的枚举和结构体),可以补充提示词:
```
请检查你生成的文档中的所有接口、结构体、枚举,这些都要在现存代码仓中真实存在且定义完全一致。对于每个接口、结构体、枚举,都要提供完整的文件路径和行号进行验证。
```
