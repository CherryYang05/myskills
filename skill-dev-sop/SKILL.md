# Agent Dev SOP

把 Agent 驱动的开发从"随手聊、随手改"固化成可复用的相位流程。核心目标：**让文档随项目演进而不漂移、不臃肿，让代码不因耦合失控而无法维护**。手段是按 decay rate 分层文档、显式做系统设计与耦合治理、用 append/supersede 替代原地改写、收尾时显式 compaction。

完整方法论说明（含背景动机、每相位的详细展开）见 `references/overview.md`；本文件是给 Agent 用的精简编排，产出文件时按下面的相位走，模板复制 `assets/` 下对应文件，细则按需读 `references/conventions.md`。

## 流程总览（8 相位）

```
【启动确认】出大纲 → 等用户确认 ─┐   ← 每次必做,确认前不产出任何文件、不进入任何相位
                              ▼
路由 → P0 需求分析 → P1 系统设计 → P2 项目初始化 → P3 模块拆分 → P4 功能设计 → P5 实现 → P6 测试与评审 → P7 收尾归档
      (EARS验收标准)  (架构/依赖方向) (AGENTS.md+护栏) (模块/功能/任务) (design+耦合评估) (测试先行,耦合治理) (测试+设计评审) (归档防漂移)
```

**铁律:技能触发后的第一个动作是出「启动大纲」并等用户确认,而不是先动手再零散追问。** 不是每次都走全程——大纲里会说明这次判定的粒度和将走的路径。

模板都在 `assets/`,产出文件时复制并填充,不要凭记忆重造模板。目录约定、拆分启发式、耦合治理、文件分类、测试策略、反漂移原则的细节在 `references/conventions.md`,需要时再读。

## 启动确认（每次必做的第一步：先出大纲,确认后执行）

技能触发后的第一个动作**不是**产出文件、**不是**零散提问,而是先输出一份「启动大纲」让用户确认。**把所有澄清集中在这一步**,确认后再进入执行,避免"先调用、再不断打断"。

### 启动大纲应包含
1. **要做什么** — 用自己的话复述本次要做的内容,确认理解一致。
2. **要求与限制** — 初步的 Goals / Non-Goals、已知约束(性能、兼容、编码标准、依赖、时间)。对话里说过的就列出;没说但你做了假设的,**显式标注「假设」**让用户校正。
3. **判定粒度 + 将走的路径** — 见下「粒度判定」。
4. **初步拆分预览**(仅大需求)— 大致分哪几个模块/功能,初判哪些功能需要写设计文档,是否需要先做系统设计。
5. **待澄清问题** — 有阻塞性的不确定点,在这里**一次性批量**提出。

### 大纲格式
```
📋 启动大纲
要做什么：<一句话复述>
要求与限制：<约束 / 假设(自己推断的标「假设」)>
判定粒度：新项目 / 中等功能 / 小修小补
将走的路径：P0 → P1(仅新项目)→ P2 → P3 → P4(功能 X、Y 需设计)→ P5 → P6 → P7
初步拆分（大需求时）：模块 A(功能 A1[需设计]、A2[直接实现])...
待澄清（如有）：<问题 1>
```

**关键:用户确认前不产出任何文件、不进入任何相位。**

## 粒度判定

| 粒度 | 信号 | 走的路径 |
|---|---|---|
| **新项目 / 大需求** | 从零搭建、涉及多子系统、需要先定边界 | P0 → P1 → P2 → P3 → P4(逐个)→ P5 → P6 → P7 |
| **中等功能**（已有项目） | 单个 feature、有非显然的设计取舍 | P0'(轻量澄清) → P4 → P5 → P6 → P7 |
| **小修小补** | bug fix、typo、显然的小改动 | 直接 P5 → 最小 P6(跑既有测试+补回归用例) → CHANGELOG |

**关键纪律:不要给小改动套重流程。** 一眼能看清解法的改动不需要设计文档；反过来,涉及多模块/并发/公共接口的改动必须过 P4,哪怕代码量不大。

粒度不明显时问一次：
```
问题：这个改动的规模？
选项：新项目/大需求(先定边界拆模块) / 单个功能(已知大方向,直接设计+实现) / 小修小补(直接改)
```

## 快速模式

仅当用户**显式**要求才启用。仍先出启动大纲(给拦截机会)但不阻塞——出完直接执行,一次性产出该粒度下的全部文档,末尾给摘要+文件列表供事后批量审。用户表现不耐烦时主动提议切换。

## P0 需求分析

复制 `assets/requirements-template.md`。核心：Context & Scope、Goals/Non-Goals(挡住自由发挥)、可验证的 Acceptance Criteria。产出 `docs/requirements/<req-slug>.md`，带 Status 头。

Acceptance Criteria 用 **EARS 句式**写并逐条编号(`AC-1`、`AC-2`…)：「当 <触发/条件> 时，系统应 <可观测行为>」。编号是后续 tasks、测试用例回链的锚点——一条 AC 应能机械地翻译成至少一条测试。

**Checkpoint:** 确认范围后再往下走。

> 中等功能走 **P0'**：不写完整需求文档,对话中 3-5 句确认 Goals/Non-Goals,并给出 3-5 条 EARS 格式的 AC(编号 AC-n,写进 design doc 的 Acceptance Criteria 小节;不够格写 design doc 的写在 tasks 文件顶部)——P5 测试先行和 P6 回链验收都以这些编号为锚点。确认后直接进 P4。

---

## P1 系统设计（仅新项目 / 架构级变更）

复制 `assets/system-design-template.md`，产出 `docs/architecture/system-design.md`。核心是画清楚：架构总览、**模块边界与依赖方向规则**（哪些依赖允许、哪些禁止）、技术选型与非功能需求、关键跨模块流程。

这是耦合治理的起点——依赖方向一旦确认就成为架构不变量，写入 AGENTS.md，后续打破必须先过 ADR。

**Checkpoint:** 确认架构总览和依赖方向规则后进 P2。中等功能跳过本相位，若发现现有边界挡路，走 ADR 而非绕开。

---

## P2 项目初始化（仅新项目）

建 `AGENTS.md`（复制 `assets/agents-template.md`）：只放慢变内容(命令/约定/架构不变量/目录地图)，绝不放进度/changelog/设计细节，软上限 ≤150 行——接近上限时把细则拆到 `docs/` 或 `references/`，AGENTS.md 只留索引和不变量。同时建文档+代码目录骨架（见 `references/conventions.md` 目录布局）。

**架构护栏工具化（强烈建议）**：把 P1 的依赖方向规则落成机械检查——按语言选依赖 lint 工具(Python: import-linter；JS/TS: dependency-cruiser；Java: ArchUnit；Go: depguard 等)，把"允许/禁止的依赖"写成规则文件，接进测试命令或 CI/hooks，让违反依赖方向变成构建失败而不是自查项。护栏命令写入 AGENTS.md 构建与测试一节。

**Checkpoint:** 展示 AGENTS.md + 目录结构(+护栏规则)，确认后进 P3。

---

## P3 模块与任务拆分

拆 模块 → 功能 → 任务 三层。模块划分服从 P1 的依赖方向；判断标准见 `references/conventions.md`（单一职责/限界上下文/依赖无环/接口先于实现）。

设计文档门槛（功能够格才写 design doc）：有非显然取舍 / 多个备选方案 / 跨模块影响或改公共接口 / 涉及并发或正确性风险。都不满足直接进 tasks。

**Checkpoint:** 确认拆分粒度和"哪些要写设计"，然后对每个够格功能走 P4。

---

## P4 功能设计（仅够格的功能）

复制 `assets/design-doc-template.md`，产出 `docs/designs/<feature-slug>.md`。除标准 section 外**必须填「耦合评估」**：新增/修改了哪些对外接口、依赖了哪些模块、是否引入依赖方向规则之外的新依赖、会不会导致循环依赖。Goals/Non-Goals 和 Alternatives Considered 必须写实。Status: Draft，实现完改 Implemented，不回头改正文。

实现细节的任务放 `docs/tasks/<feature>.md`（复制 `assets/tasks-template.md`），不要混进 design doc。

**Checkpoint:** 每篇设计确认后再进 P5。

---

## P5 实现

按 design doc + tasks 实现。四条通用纪律：

- **测试先行**：写实现之前，先从 AC(EARS 编号) + design doc 的 Failure Modes 生成会失败的测试骨架，再实现到测试通过——给实现一个可验证的目标，防止"写完就宣布完成"。
- **文件分类**：feature-based / layer-based 二选一并全项目统一，遵循 AGENTS.md 目录地图；文件只承担一种变化原因，过大/职责混杂就拆。
- **耦合治理**：优先跑 P2 建的依赖护栏工具；无护栏的项目编码中/PR 前过一遍 `assets/coupling-checklist.md`（依赖方向、接口隔离、依赖注入、避免上帝文件、限制扇出）。
- **上下文与并行**：高噪音探索(通读大量代码、外部调研)下放 subagent，保护主上下文；P3 拆分后无依赖关系的模块可并行实现(多 agent + git worktree)；上下文接近装满时先把状态落盘到 docs/tasks/ 或 .agent-scratch 再继续。

发现设计需调整就回 P4 更新（Draft 阶段直接改正文），不要让代码和设计分叉。边实现边勾 tasks 的 checkbox。

---

## P6 测试与评审

- **单元测试**：覆盖 P0 验收标准的核心路径 + design doc 的 Failure Modes；粒度对应模块边界，不跨模块；只 mock 边界外依赖。
- **集成测试**：覆盖 P1 系统设计里的关键跨模块流程 + design doc 标"跨模块影响"的功能；被多方依赖的接口做契约测试。
- **设计符合性评审**：用全新上下文(subagent)对照 design doc 审本次 diff——实现是否偏离设计、耦合评估承诺是否兑现、有无 Non-Goals 之外的顺手改动。新上下文不带实现时的偏见，最能发现代码与设计的分叉。
- **回链验收**：按 AC 编号逐条对照测试结果打勾，AC ↔ 测试一一对应，不靠感觉判断完成。

**Checkpoint:** 单元+集成测试通过、评审无未解决问题、AC 全部满足才进 P7。

---

## P7 收尾归档（防漂移关键相位，不可省）

逐项做：
1. `docs/designs/<feature>.md` Status → Implemented（被替代的 → Obsolete + Supersedes）
2. CHANGELOG append 一行，不改旧条目
3. 引入新稳定约定就精简更新 AGENTS.md，同时删过时内容，检查软上限
4. **依赖图复查**：跑依赖护栏工具确认无未经批准的新跨模块依赖/循环依赖(无护栏项目人工复查)
5. 清理已完成的 `docs/tasks/`、清空 `.agent-scratch`
6. 归档(可选)：完成的需求/设计/任务移进 archive

产出小结：本次收尾改了哪些文档、依赖图有无变化。

## 偏差处理

| 用户行为 | 应对策略 |
|---|---|
| 任何触发 | 先出启动大纲、等确认，再执行 |
| "别问了直接走" | 切快速模式：仍出大纲但不阻塞 |
| 丢来一句模糊需求 | 大纲里复述理解+标假设+批量待澄清，等确认 |
| 只想改某个已有文档局部 | 直接局部改，不触发整套流程 |
| 小 bug 却想走全流程 | 提示这是小修小补，建议直接 P5 |
| 每个 trivial 功能都要设计文档 | 用 P3 门槛劝阻 |
| 想把进度写进 AGENTS.md | 拦下，引导到 docs/tasks/ 或 CHANGELOG |
| 编码中发现要打破架构不变量 | 先写 ADR，批准后再改 |
| 已有项目但没 AGENTS.md/系统设计 | 提议先补 P2（可逆向生成 baseline），必要时补 P1 |
| 拆分中发现循环依赖 | 停下解决，不用 hack 掩盖 |
| 实现中上下文接近装满 | 状态落盘到 tasks/scratch，必要时开新会话续做 |
