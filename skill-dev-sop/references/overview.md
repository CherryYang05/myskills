# Agent 驱动软件开发标准流程（通用 SOP）

> 适用范围：不绑定语言、框架、项目规模。个人独立开发到多人协作团队均可用。
> 前身：本 SOP 在 `skill-dev-flow` 的六相位框架基础上扩展而来，新增「系统设计」独立相位，
> 并把「代码耦合治理」「文件与目录分类」「单元/集成测试」从原来的隐含内容显式拆出，
> 因为这三项正是 AI 大量写代码后最先失控、也最难事后补救的部分。

## 0. 为什么需要这套流程

AI 写代码有一个和人类工程师不同的失效模式：**它没有连续记忆，只有当次上下文。** 每次会话都是一次"失忆后重建理解"。项目小的时候这无所谓——AI 扫一遍代码就能重建全貌。项目一旦变大，会发生三件事同时失控：

1. **上下文装不下全貌**，AI 只能看到局部，于是基于局部认知做出全局不一致的改动（重复实现、破坏未见到的约定、引入循环依赖）。
2. **没有显式记录"为什么这样设计"**，AI 改代码时看不到历史决策的理由，于是要么盲目遵从旧代码（哪怕它已过时），要么随意推翻（哪怕它是刻意的权衡）。
3. **文档和代码各自漂移**，因为没人规定"什么内容该写在哪、写完之后怎么维护"，文档要么不写，要么写了没人更新，很快变成噪音甚至误导。

这套 SOP 的核心手段就两条：

- **让"人类需要长期记住的东西"显式落地成文件**，按变化速率（decay rate）分层存放，而不是全塞进一个 README 或指望 AI 的上下文记住。
- **用相位（phase）把"想清楚"和"动手改"分开**，每个相位有明确的产出物和确认点（checkpoint），下一相位才允许开始。这样 AI 每次介入时，只需要读该相位需要的那一份文件，而不是整个项目历史。

---

## 1. 流程总览

```
启动确认 ──▶ 需求分析(P0) ──▶ 系统设计(P1) ──▶ 项目初始化(P2) ──▶ 模块与任务拆分(P3)
                                                                        │
        ┌───────────────────────────────────────────────────────────┘
        ▼
   功能设计(P4，仅够格的功能) ──▶ 编码实现(P5) ──▶ 测试验证(P6) ──▶ 收尾归档(P7)
```

粒度判定同样适用：

| 粒度 | 信号 | 走的相位 |
|---|---|---|
| 新项目 / 大需求 | 从零搭建，或涉及多子系统 | 启动确认 → P0 → P1 → P2 → P3 → P4(逐个) → P5 → P6 → P7 |
| 中等功能（已有项目） | 单个 feature，有非显然取舍 | 启动确认 → 轻量 P0 → P4 → P5 → P6 → P7 |
| 小修小补 | bug fix、typo、显然改动 | 直接 P5 → 最小 P6（跑既有测试 + 补一个回归用例）→ CHANGELOG 一行 |

**铁律不变：不要给小改动套重流程。** 一眼能看清解法的改动不需要系统设计或功能设计文档；反过来，涉及多模块、并发、公共接口的改动，哪怕代码量不大，也必须过 P4（功能设计）。

## 2. 启动确认（每次介入的第一步）

在做任何设计或编码之前，先用一份「启动大纲」和用户/需求方对齐，避免"先动手再返工"：

```
📋 启动大纲
要做什么：<一句话复述>
要求与限制：<已知约束 + 自己推断的假设，标注「假设」>
判定粒度：新项目 / 中等功能 / 小修小补
将走的相位：P0 → P1 → ...
初步拆分（大需求时）：模块 A（功能 A1[需设计]、A2[直接实现]）...
待澄清：<一次性批量列出阻塞性问题>
```

输出后停下等确认。确认前不产出任何设计文件、不写任何代码。这一步比事后返工便宜得多，代价被低估的原因通常是"觉得需求已经很清楚了"——但 AI 的理解和人的理解之间的落差，正是后期返工的主要来源。

---

## 3. 阶段 P0：需求分析

把模糊诉求变成结构化、可验证的需求。产出 `docs/requirements/<slug>.md`（模板见 `assets/requirements-template.md`），核心是三件事：

- **Context & Scope**：为什么做、影响范围、关联哪些现有模块。三段以内讲清楚，让读者不依赖对话历史就能理解。
- **Goals / Non-Goals**：Non-Goals 比 Goals 更重要。它是挡住 AI"顺手多做"和范围蔓延的护栏。留空是危险信号——几乎所有需求都有该划清的边界。
- **验收标准（Acceptance Criteria）**：必须可验证，最好能直接对应到一条测试用例。写"性能要好"这种无法判定的目标等于没写。

**Checkpoint：** 展示需求文档，确认范围后再进入系统设计。边界没定就往下走，等于让 AI 拆解一个中途会变形的目标。

---

## 4. 阶段 P1：系统设计（新增相位，仅新项目 / 架构级变更需要）

这是原流程里缺失、也是大项目最容易失控的一环。系统设计解决的问题是：**在拆模块之前，先把"模块之间怎么依赖、边界画在哪、允许什么样的耦合"定下来**，否则后面每个功能都会按局部最优拆分，长期堆出一张依赖关系网。

产出 `docs/architecture/system-design.md`（模板见 `assets/system-design-template.md`），至少包含：

### 4.1 架构总览
一段话 + 一张分层/分组件图，说明系统由哪些顶层部分组成、各自职责、数据如何流动。图不追求精美，能让新加入的人（或下一次接手的 AI）5 分钟建立心智模型即可。

### 4.2 模块边界与依赖方向
这是耦合治理的起点。明确写出：

- 每个模块对外暴露什么（接口/API/事件），隐藏什么（内部实现）。
- **依赖方向规则**：哪些模块允许依赖哪些模块，反向依赖是否禁止。常见规则如"上层可以依赖下层，下层不能反向依赖上层"（分层架构），或"领域层不依赖任何基础设施细节，基础设施实现领域层定义的接口"（依赖倒置 / 六边形架构）。
- 显式画出**禁止的依赖**（比如"UI 层不能直接访问数据库"），比只画允许的依赖更有效——它是后续代码评审和 AI 自查的硬约束。

### 4.3 技术选型与非功能需求
语言/框架/存储/通信协议的选择及理由（一句话够，理由记入 ADR）；性能、可用性、安全、可扩展性方面的硬性指标（有则写，没有就明确写"暂无特殊要求"，避免被误解为遗漏）。

### 4.4 关键跨模块流程
挑 2-4 条最核心的调用链（如"用户下单"从入口到落库的完整路径），画时序图或列步骤。这类流程是集成测试（P6）的直接依据。

**Checkpoint：** 系统设计一旦确认，模块边界和依赖方向规则就成为**架构不变量**，写入 AGENTS.md（见 P2），后续任何想打破它的改动都必须先过 ADR，而不能在某次功能实现里悄悄破例。

> 中等功能不需要重新做系统设计，但如果发现现有边界挡住了实现路径，说明可能需要一次小范围的架构决策——走 ADR，而不是绕开边界硬塞。

## 5. 阶段 P2：项目初始化（仅新项目）

建立小而稳的 `AGENTS.md` 和文档/代码骨架，一次性完成，之后很少大改。

### AGENTS.md 铁律
只放**慢变**内容：构建/测试命令、代码约定、架构不变量（来自 P1）、目录地图。**绝不放**：进度、changelog、某功能设计细节、临时笔记——这些各有归处，混进来是文档臃肿的起点。软上限 ≤150 行，接近上限就 prune 或把细节移到 `references/`。

模板见 `assets/agents-template.md`。

### 目录骨架（文档 + 代码两部分）

```
项目根/
├── AGENTS.md                    # 慢变：命令/约定/架构不变量/目录地图
├── CHANGELOG.md                 # 历史：append-only
├── .agent-scratch               # 显式临时区，定期清空
├── docs/
│   ├── architecture/            # 系统设计文档（P1），项目级，极少改
│   ├── requirements/            # 结构化需求（P0），point-in-time，带 Status
│   ├── designs/                 # 功能设计文档（P4），point-in-time，带 Status
│   ├── decisions/                # ADR，append-only，supersede 不 edit
│   └── tasks/                    # 任务清单，ephemeral
└── src/（或语言约定的源码根）
    └── <按 P3 的文件分类规则组织>
```

**Checkpoint：** 展示 AGENTS.md + 目录结构，确认后进 P3。

## 6. 阶段 P3：模块划分与任务拆分

### 6.1 拆分三层
- **模块**：按职责/边界切，系统级项目按子系统切。模块划分必须服从 P1 定的依赖方向，不能为了"这次实现方便"临时开一条新依赖。
- **功能**：模块下的具体能力，是设计和实现的基本单位。
- **任务**：功能下可独立完成、可验证的步骤。太粗（"实现整个功能"）要拆开，太细（"加一个分号"）要合并。

### 6.2 模块划分的判断标准（高内聚低耦合的可操作化）
判断一个模块划分是否合理，用这几条代替"感觉":

- **单一职责**：模块内的代码是否因为同一个原因变化。如果一个模块会因为"UI 需求变了"和"数据库换了"两种完全不相关的原因都要改，说明职责没分干净。
- **限界上下文（bounded context）**：模块内部用的术语/数据模型是否自洽，不需要向外部模块借用概念。同一个词（如"用户"）在不同模块里含义不同是正常的，前提是每个模块内部一致。
- **依赖方向无环**：模块依赖图必须是有向无环图（DAG）。出现循环依赖（A 依赖 B，B 又依赖 A）是架构报警信号，必须在拆分阶段解决，不要指望编码时用局部 hack（延迟加载、全局单例）掩盖。
- **接口先于实现**：模块间交互先定接口/契约，再各自实现。这样功能设计文档里的 Interfaces 一节才有意义，也是并行开发和后续替换实现的前提。

### 6.3 设计文档门槛
功能需要单独写设计文档，当且仅当满足任一：有非显然的设计取舍；有多个值得记录的备选方案；跨模块影响或改动公共接口；涉及并发/内存序/正确性风险。都不满足就不写，直接进任务清单——给每个 trivial 功能都配设计文档，是 `docs/designs/` 臃肿的主因。

**Checkpoint：** 确认拆分粒度和"哪些功能需要设计"，然后对每个够格的功能走 P4。

## 7. 阶段 P4：功能设计（仅够格的功能）

复制 `assets/design-doc-template.md`，产出 `docs/designs/<feature-slug>.md`。相比原模板，本 SOP 在设计文档里显式加了一节：

### 耦合评估（新增小节）
每篇设计文档必须回答：
- 本功能新增/修改了哪些对外接口？
- 依赖了哪些模块？是否引入了 P1 依赖方向规则之外的新依赖？
- 会不会导致循环依赖？如果会，怎么解决（拆接口、引入事件/回调、提取共享模块）？

这一节存在的理由：耦合问题几乎都是在设计阶段悄悄引入的，编码阶段发现已经太晚。把它做成设计文档的强制小节，相当于给耦合治理设了一道前置闸门。

**Goals/Non-Goals** 和 **Alternatives Considered** 必须写实，这是防止 AI 自由发挥、重复推翻已否决方案的关键。文档头部带 `Status: Draft`，完成后改成 `Implemented`，不回头改正文——这是防漂移的核心机制。

**Checkpoint：** 每篇设计确认后再进编码。

---

## 8. 阶段 P5：编码实现

按设计文档 + 任务清单实现。这一相位的重点不是"怎么写代码"（那是语言/框架层面的事），而是两条通用纪律：**文件分类**和**耦合治理**——这两项一旦在编码阶段失控，后面很难低成本修复。

### 8.1 文件与目录分类规范

选一种分类原则并全项目统一，不要混用：

- **按功能/领域分类（feature-based）**：`user/`、`order/`、`payment/`，每个目录下自带该功能的接口、实现、测试。优点是改一个功能只碰一个目录，AI 单次上下文就能看全；扩展新功能不影响旧目录。项目变大后推荐这种。
- **按技术层分类（layer-based）**：`controllers/`、`services/`、`repositories/`。优点是同类代码集中，便于统一规范；缺点是改一个功能要跨多个目录跳转，项目变大后 AI 容易漏改某一层。

**判断依据：** 团队/AI 协作为主、功能迭代频繁 → 优先 feature-based；技术关注点分离本身就是核心诉求（如需要严格的分层测试替身）→ layer-based，或两者结合（大目录按 feature，目录内部再按 layer）。

**文件级红线**（不分方案都适用）：
- 一个文件只承担一种"变化原因"，文件过大（如超过几百行、职责明显混杂）是拆分信号，不要靠"以后再重构"拖延。
- 测试文件与被测代码保持可预测的对应关系（同名同目录，或镜像的 `tests/` 结构），让 AI 能一次定位到对应测试，不用搜索。
- 公共/共享代码单独成目录（`common/`、`shared/`），并且这个目录只能被依赖、不能反向依赖业务模块——它本身也要遵守 P1 的依赖方向规则。

### 8.2 代码耦合治理（可执行的检查项，不止是原则）

编码中 / PR 前，用这几条自查代替模糊的"低耦合"口号：

- **依赖方向**：新增的 import/引用是否符合 P1 定的方向规则？违反了，是先改设计（走 ADR）还是重构，不要默许"这次先这样"。
- **接口隔离**：调用方是否被迫依赖了它不需要的方法？一个大而全的接口比多个小接口更容易产生不必要的耦合。
- **依赖注入优于硬编码依赖**：模块需要的外部依赖（数据库连接、其他服务客户端）通过参数/构造函数传入，而不是在内部直接 `new`/`import` 具体实现，这样才能在测试中替换，也是解耦的直接手段。
- **避免"上帝文件/上帝类"**：一个文件/模块承担了过多职责（既处理输入校验，又处理业务逻辑，又处理持久化）是耦合的常见来源，拆分优先于加参数、加 if 分支。
- **限制扇出（efferent coupling）**：一个模块同时依赖的其他模块数量过多，说明它可能在做"协调"之外的事，考虑引入一个专门的协调层，或重新审视职责划分。

实现中发现设计需要调整，回 P4 更新设计文档（Draft 阶段直接改正文），不要让代码和设计悄悄分叉——这是防漂移原则在编码阶段的体现。

边实现边勾 `docs/tasks/<feature>.md` 的 checkbox，这是 ephemeral 区，放心改。

## 9. 阶段 P6：测试验证

从实现中显式拆出来强调，因为"没有独立测试相位"是 AI 写代码最常跳过的一步——它倾向于写完代码就认为完成了。

### 9.1 单元测试
- **测什么**：覆盖 P0 的验收标准对应的核心路径，以及 P4 设计文档里的 Failure Modes（边界/失败路径）。不为覆盖率数字堆无意义的测试。
- **测试粒度对应模块边界**：单元测试测的是单个模块/函数的行为，不跨模块。跨模块的验证放到集成测试，避免单元测试因为无关模块的变化而频繁失败（这是耦合在测试层面的体现，值得警惕）。
- **Mock 策略**：只 mock 掉模块边界之外的依赖（如外部 API、数据库），不要 mock 被测模块内部的实现细节——过度 mock 会让测试对重构失去防护作用。
- **与文件分类的对应**：测试文件位置遵循 8.1 定的规则，保证 AI 改代码时能顺带找到并更新对应测试。

### 9.2 集成测试
- **测什么**：P1 系统设计里列出的关键跨模块流程（4.4 节），以及 P4 设计文档里标注"跨模块影响"的功能。
- **契约测试**：模块间的接口/契约本身值得单独测试（尤其是被多个调用方依赖的接口），保证任何一方改实现不破坏契约。
- **环境与数据**：明确集成测试跑在什么环境（内存态/容器化依赖/测试环境），用的是真实依赖还是受控的测试替身，避免"测试通过但生产环境失败"的落差。

### 9.3 回链验收标准
测试完成后，回到 P0 的 Acceptance Criteria 逐条打勾——这是"完成"判定的权威来源，不要靠感觉判断需求做完了。

**Checkpoint：** 单元测试 + 集成测试通过、验收标准全部满足，才进入 P7。

---

## 10. 阶段 P7：收尾归档（防漂移的关键相位，不可省略）

不指望前面的增量编辑保持文档干净，收尾时做一次显式 compaction：

1. **标 Status**：`docs/designs/<feature>.md` 头部 Status 改成 `Implemented`（被替代的标 `Obsolete` 并填 `Supersedes`）。
2. **更 CHANGELOG**：append 一行——做了什么、对应哪个 design/req，绝不改旧条目。
3. **prune AGENTS.md**：引入了新的稳定约定/命令/目录就精简更新；同时删掉已过时的内容；检查是否超软上限。
4. **依赖图复查**：本次改动有没有悄悄引入新的跨模块依赖或循环依赖？如果有且未经 ADR 批准，这里是最后一道拦截关口。
5. **清 tasks/scratch**：已完成的 `docs/tasks/` 文件可删或归档，清空 `.agent-scratch`。
6. **归档**（可选）：完成的需求/设计/任务移进 archive 目录，保留 why。

产出小结：本次收尾改了哪些文档（哪篇设计标了 Implemented、CHANGELOG 加了什么、AGENTS.md 精简了什么、依赖图有无变化）。

| 内容类型 | 存放位置 | 变化速率 | 写操作语义 |
|---|---|---|---|
| 命令/约定/架构不变量/目录地图 | `AGENTS.md` | 慢变 | 谨慎编辑 + 定期 prune |
| 系统架构总览 | `docs/architecture/` | 极慢变 | 大版本迭代才改，改动大就走 ADR |
| 结构化需求 | `docs/requirements/` | 阶段性快照 | 写一次，靠 Status 标生命周期 |
| 功能设计（含耦合评估） | `docs/designs/` | 阶段性快照 | 同上 |
| 架构决策 | `docs/decisions/`（ADR） | 历史 | append + supersede，绝不 edit |
| 变更历史 | `CHANGELOG.md` | 历史 | append-only |
| 任务清单/临时笔记 | `docs/tasks/`、`.agent-scratch` | ephemeral | 随意重写 |

**核心原则只有一条：不同变化速率的内容物理隔离，各用各的写操作语义。** 文档臃肿和漂移几乎都源于违反这条——把 ephemeral 的进度写进慢变的 AGENTS.md，或者拿"回头改正文"的方式维护本该是快照的设计文档。

---

## 12. 反漂移红线（贯穿全流程的检查清单）

- AGENTS.md 绝不写进度、changelog、某功能设计细节——发现了立刻挪走。
- 需求/设计文档是快照，Implemented 后不回头改正文；要变更就写新版本并 supersede。
- ADR、CHANGELOG 只 append，历史决策不可篡改。
- "哪些做完了"的权威来源是任务清单/代码/测试本身，不要在多份 markdown 里手工同步进度——两份真相必然漂移。
- 模块依赖方向违反 P1 规则时，先走 ADR 再改代码，不要在某次功能实现里默许例外。
- 每次收尾（P7）必须显式做一次 compaction，不能假设增量编辑会自然保持整洁。

---

## 13. 常见偏差与应对

| 情况 | 应对 |
|---|---|
| 小 bug 却想走全流程 | 提示这是小修小补，建议直接 P5 + 补回归测试 + CHANGELOG 一行 |
| 每个 trivial 功能都要写设计文档 | 用 6.3 的门槛劝阻，说明会导致 `docs/designs/` 臃肿 |
| 想把进度/changelog 写进 AGENTS.md | 拦下，引导到 `docs/tasks/` 或 CHANGELOG |
| 编码中发现要打破架构不变量 | 先写 ADR 说明理由，批准后再改，不要静默违反 |
| 已有项目但没有 AGENTS.md / 系统设计文档 | 先补一次 P2（可基于现有代码逆向生成 baseline），必要时补 P1 |
| 模块拆分中发现循环依赖 | 停下解决——拆接口、引入事件机制、提取共享模块，不要用延迟加载等 hack 掩盖 |
