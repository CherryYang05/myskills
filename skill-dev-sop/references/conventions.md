# Conventions — 目录布局 / 拆分启发式 / 耦合与文件分类 / 测试策略 / 反漂移原则

> 本文件供 SKILL.md 按需加载。SKILL.md 是流程编排，本文件是细则。
> 在 skill-dev-flow 的 conventions.md 基础上扩展了「系统设计目录」「耦合治理」「代码文件分类」「单元/集成测试」四节。

## 目录布局（文档 + 代码）

```
项目根/
├── AGENTS.md                # 慢变。命令/约定/架构不变量/目录地图。小而稳，≤~150 行。
├── CHANGELOG.md             # 历史。append-only，新条目置顶或置底但绝不改旧条目。
├── .agent-scratch           # 显式临时区。Agent 随便写，定期清空。
├── docs/
│   ├── architecture/        # 系统设计文档（P1）。极慢变，point-in-time，带 Status 头。
│   │   └── system-design.md
│   ├── requirements/        # 结构化需求（P0）。point-in-time，带 Status 头。
│   │   └── <req-slug>.md
│   ├── designs/              # 每个够格的功能一篇设计文档（P4）。point-in-time，带 Status 头。
│   │   └── <feature-slug>.md
│   ├── decisions/            # ADR。append-only，supersede 不 edit。
│   │   └── NNNN-<title>.md
│   └── tasks/                 # 任务清单（P4/P5）。ephemeral，随便勾改删。
│       └── <feature-slug>.md
└── src/（或语言约定的源码根）
    └── <按下方「代码文件分类」组织>
```

每个目录对应一种 decay rate，这是整套布局的核心：**不同变化速率的内容物理隔离，各用各的写操作语义。**

| 目录 | decay rate | 写操作语义 |
|---|---|---|
| AGENTS.md | 慢变 | 谨慎编辑 + 定期 prune |
| docs/architecture | 极慢变 | point-in-time，改动大就走 ADR |
| docs/requirements、docs/designs | 阶段性（快照） | 写一次，靠 Status 标生命周期，不回头改正文 |
| docs/decisions（ADR） | 历史 | append + supersede，绝不 edit |
| CHANGELOG | 历史 | append-only |
| docs/tasks、scratch | ephemeral | 随意重写 |

## 拆分启发式（P3 用）

### 三层拆分
1. **模块（module）** — 按职责和边界切；系统级项目按子系统切（如存储引擎 / 网络 / 共识）。必须服从 P1 系统设计定的依赖方向。
2. **功能（feature）** — 模块下的具体能力，是设计与实现的基本单位。
3. **任务（task）** — 功能下可执行、可验证的步骤。

### 模块划分判断标准
- **单一职责**：模块内代码是否因同一个原因变化，不同原因混在一起是拆分信号。
- **限界上下文**：模块内部术语/数据模型自洽，不向外部借概念。
- **依赖方向无环**：模块依赖图必须是 DAG，出现循环依赖立即在拆分阶段处理。
- **接口先于实现**：模块间交互先定契约，各自再实现。

### 设计文档门槛
功能**需要**单独写 design doc，当且仅当满足任一：
- 有非显然的设计取舍（多种数据结构 / 接口 / 算法可选）
- 有多个值得记录的备选方案
- 跨模块影响，或改动公共接口 / 契约
- 涉及并发、内存序、正确性 / 一致性风险

都不满足 → 不写设计文档，直接进 tasks。

> 反例（不该写设计文档）：给已有结构体加一个字段、修一个空指针、改一处日志格式、CRUD 包装。
> 正例（该写）：新的并发数据结构、改动 RPC 契约、引入新的状态机、有多种实现路径的算法、新增跨模块依赖。

### 任务颗粒度
- 每条 task 能独立完成且可验证（有明确的"做完了"判据）。
- 太粗（如"实现整个功能"）→ 拆开。
- 太细（如"加一个分号"）→ 合并进相邻 task。

## 耦合治理（P4 设计 / P5 实现共用）

耦合问题的本质：模块之间的改动传播范围过大。判断和控制手段：

- **依赖方向规则**：P1 系统设计定义"谁能依赖谁"，任何新依赖先对照这条规则；违反了先走 ADR，不要在实现中默许例外。
- **接口隔离**：调用方不应被迫依赖它不需要的方法；大而全的接口是不必要耦合的常见来源。
- **依赖注入优于硬编码依赖**：外部依赖通过参数/构造函数传入，不在内部直接实例化具体实现——这是可测试性和解耦的共同前提。
- **避免上帝文件/上帝类**：一个文件/模块职责过多（校验+业务逻辑+持久化混在一起）时，拆分优先于继续加分支。
- **限制扇出**：一个模块同时依赖过多其他模块，通常说明它在做"协调"之外的事，考虑抽出协调层。
- **循环依赖是硬报警**：一旦出现，停下解决（拆接口 / 事件回调 / 提取共享模块），不要用延迟加载、全局单例等手段掩盖。

编码期用 `assets/coupling-checklist.md` 逐项自查；设计期在 design doc 的"耦合评估"小节里提前想清楚。

## 代码文件分类（P5 用）

选一种分类原则并全项目统一：

| 分类方式 | 目录示例 | 适合场景 |
|---|---|---|
| 按功能/领域（feature-based） | `user/`、`order/`、`payment/`，各自带接口+实现+测试 | Agent/多人协作为主、功能迭代频繁、项目会持续变大 |
| 按技术层（layer-based） | `controllers/`、`services/`、`repositories/` | 技术关注点分离本身是核心诉求、需要严格的分层测试替身 |
| 混合 | 大目录按 feature，目录内部再按 layer | 中大型项目的常见折中 |

**文件级红线：**
- 一个文件只承担一种"变化原因"，明显职责混杂或体积过大是拆分信号，不要靠"以后重构"拖延。
- 测试文件与被测代码保持可预测的对应关系（同名同目录，或镜像的 `tests/` 结构）。
- 公共/共享代码单独成目录（`common/`/`shared/`），只能被依赖、不能反向依赖业务模块，本身也要遵守依赖方向规则。

## 测试策略（P6 用）

### 单元测试
- 覆盖 P0 验收标准对应的核心路径 + design doc 的 Failure Modes。
- 测试粒度对应模块边界，不跨模块；跨模块验证放到集成测试。
- Mock 只覆盖模块边界之外的依赖，不 mock 被测模块内部实现细节。
- 测试文件位置遵循"代码文件分类"的对应规则。

### 集成测试
- 覆盖系统设计里的关键跨模块流程 + design doc 标注"跨模块影响"的功能。
- 被多方依赖的接口/契约单独做契约测试。
- 明确测试环境（内存态/容器化依赖/测试环境）和依赖是真实还是受控测试替身。

### 回链
测试完成后逐条对照 P0 的 Acceptance Criteria 打勾——这是"完成"判定的权威来源，不是感觉。

## 反漂移原则（贯穿全流程，P7 集中体现）

文档臃肿/漂移的根因：**把不同 decay rate 的内容塞进同一文件，再用原地增删去维护它。** 五条原则对症：

1. **按 decay rate 物理拆分** — 一个文件只承担一种生命周期（见目录布局）。
2. **历史和决策 append + supersede，不 edit** — ADR 一旦写下不可变；要改写新条目标 supersedes。CHANGELOG 同理。
3. **状态尽量派生，不维护第二份真相** — "哪些做完了"的权威来源是 tasks / issue / PR / 测试 / 代码本身，不要手工同步进多份 markdown。
4. **设计/需求文档是快照，靠 Status 标生命周期** — Draft 阶段可改；一旦 Implemented 就冻结，后续变化写新文档并 supersede。
5. **依赖方向和架构不变量不可静默打破** — 打破必须先有 ADR，写入 AGENTS.md 的"架构不变量"一节才算生效。

### P7 收尾时的 compaction checklist
- `docs/designs/` design doc Status → Implemented（被替代的 → Obsolete + Supersedes）
- CHANGELOG append 一行（做了什么 + 关联 design/req），不改旧条目
- 引入新稳定约定/命令/目录 → 精简更新 AGENTS.md，同时删过时内容，检查软上限
- 依赖图复查：本次是否引入未经批准的新跨模块依赖或循环依赖
- 已完成 `docs/tasks/` 删/归档，清空 .agent-scratch

### AGENTS.md 卫生红线
绝不写进 AGENTS.md：进度（done/doing/todo）、changelog、某个功能的设计细节、临时笔记。
这些各有归处（docs/tasks / CHANGELOG / docs/designs / scratch）。混进来就是臃肿的起点。
