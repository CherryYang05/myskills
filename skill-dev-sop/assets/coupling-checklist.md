# 耦合自查清单 — <功能/PR 名称>

关联设计：docs/designs/<feature-slug>.md（若有）
关联系统设计：docs/architecture/system-design.md

## 依赖方向

- [ ] 新增的 import / 引用是否符合系统设计里定义的依赖方向规则？
- [ ] 是否引入了新的跨模块依赖？如果有，是否在设计文档的"耦合评估"里记录过？
- [ ] 是否产生了循环依赖（A 依赖 B，B 又依赖 A）？

> 违反依赖方向规则时：先写 ADR 说明理由并获批准，再改代码；不要默许"这次先这样"。

## 接口与依赖注入

- [ ] 调用方是否被迫依赖了它不需要的方法？（考虑拆小接口）
- [ ] 外部依赖（数据库连接、其他服务客户端）是否通过参数/构造函数传入，而非内部硬编码 new/import？

## 文件与职责

- [ ] 改动是否让某个文件/类承担了明显不相关的多种职责（上帝文件/上帝类信号）？
- [ ] 文件是否因为改动明显变大（职责混杂）？是否应该拆分？

## 扇出（efferent coupling）

- [ ] 本次改动后，该模块同时依赖的其他模块数量是否显著增加？
- [ ] 如果扇出过高，是否需要引入一个专门的协调层，而不是让当前模块继续膨胀？

## 结论

- [ ] 以上自查全部通过，或问题已记入 ADR / 设计文档并获批准。
