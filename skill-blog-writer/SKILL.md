# Tech Blog Writer

将技术对话整理成发布级博客文章的技能。通过四阶段协作流程，确保博客准确、完整、对外部读者友好。

## 四阶段流程总览

1. **类型确认**：确定博客类型（教程 / 技术深度解析）
2. **素材提取与大纲确认**：从对话中提取要素，生成大纲，用户确认后再动笔
3. **生成与迭代**：按大纲逐段生成，用户可中途纠偏
4. **质量检查与交付**：读者视角审查 + 生成可下载文件

---

## 快速模式

如果用户说"快速出一篇"、"别问了直接写"、"不用确认直接生成"等，跳过阶段 1-2 的交互，直接走：自动判断博客类型 → 提取素材 → 生成全文 → 质量自检 → 交付文件。不在对话中输出全文预览，只给摘要 + 下载链接。

如果用户在任何阶段表现出不耐烦（"差不多就行"、"太慢了"），主动提议切换到快速模式。

---

## 阶段 1：类型确认

如果用户**明确指定**了类型（"教程"/"技术解析"），直接跳到阶段 2。

如果用户**未指定**，使用 `ask_user_input_v0` 工具弹出选择框询问：

```
问题：这篇博客是哪种类型？
选项：
  - 教程 / How-to（工具使用、环境配置、操作步骤）
  - 技术深度解析（原理分析、源码阅读、设计决策）
```

---

## 阶段 2：素材提取与大纲确认

### 第一步：通读对话，提取要素

通读整个对话，提取以下要素：
- **核心问题/主题**：这次对话在解决什么问题？
- **关键知识点**：涉及哪些概念、原理、工具？
- **过程脉络**：问题是如何被分析和解决的？
- **结论与收获**：最终达成了什么？有哪些值得记录的结论？
- **踩坑记录**：对话中出现了哪些报错、误解、走弯路？

**范围控制**：单篇博客只围绕一个核心主题展开。对话中的延伸讨论和概念科普，如果独立成文更合适就不要塞进来，文末一句话提及即可。

### 第二步：补充上下文（按需）

如果对话中引用了之前讨论过的概念但本次未充分展开（比如"上次分析过的 Paxos 提交流程"），使用 `conversation_search` 搜索历史对话，补充关键背景信息。

如果搜索到了有价值的补充内容，在大纲中标注"[补充自历史对话]"，让用户知道哪些内容来自其他对话。

不要默默补充——告诉用户搜到了什么，让用户决定是否采纳。

### 第三步：输出大纲，等待确认

将提取的要素组织成大纲，**在对话中展示给用户**，格式如下：

```
📋 博客大纲

**标题**：[拟定标题]
**类型**：教程 / 技术深度解析
**核心主题**：[一句话]

**章节结构**：
1. [章节名] — [该章节要覆盖的要点，1-2 句话]
2. [章节名] — [要点]
3. ...

**计划包含的代码/配置片段**：
- [片段 1 简述]
- [片段 2 简述]

**踩坑记录**：[是否包含，包含哪些]

**不打算包含的内容**：[对话中讨论过但不放进本文的内容，及原因]
```

然后等用户确认。用户可能会：
- 直接说"可以"/"没问题" → 进入阶段 3
- 调整章节顺序、增删章节、修改标题 → 更新大纲后再次确认
- 补充对话中没提到的额外信息 → 纳入大纲

**关键**：不要在用户确认前开始写正文。大纲是轻量级的，调整成本低；全文写完再改，成本高。

---

## 阶段 3：生成与迭代

### 生成策略

基于确认后的大纲，生成完整博客 Markdown。

**不在对话中输出全文**——直接用 `create_file` 生成 `.md` 文件并用 `present_files` 提供下载链接，对话中只给一段简短摘要（3-5 句话概述博客内容和亮点）。

原因：博客通常 1000-3000 字，在对话中预览既冗长又不方便编辑，不如直接看文件。

### 迭代修改

交付文件后，询问用户是否需要修改。如果用户反馈修改意见：
- 用 `str_replace` 精确修改文件中的对应内容（不要重新生成全文）
- 每次修改后重新 `present_files` 提供更新后的文件
- 如果用户的修改意见涉及结构性调整（如增删章节），先确认调整方案再执行

持续迭代直到用户满意。如果连续 3 轮没有实质性修改，主动问一句"还有要改的吗？没有的话我做最后的质量检查"。

---

## 阶段 4：质量检查与交付

### 读者视角检查

在用户确认内容满意后（或快速模式下生成完毕后），AI 重新审视全文，**假设自己是第一次接触该主题的工程师**，检查以下问题：

1. **前置知识跳跃**：是否有未解释就直接使用的概念？（对话双方共享的背景知识，外部读者可能不知道）
2. **因果链断裂**：读者能否仅凭博客内容理解"为什么要这样做"？
3. **代码片段上下文**：代码块是否缺少必要的文件路径、函数签名、调用上下文？
4. **术语首次出现**：技术术语首次出现时是否有简要说明？

如果发现问题，列出具体问题并提出修复建议，等用户确认后修复。如果没有问题，直接进入最终交付。

### 自检清单

生成后自查（不输出给用户，AI 内部执行）：
- [ ] 标题是否准确描述了内容？（教程用动词开头，解析用名词短语）
- [ ] 标题是否包含具体技术栈/工具名？（利于检索）
- [ ] 背景章节是否说清楚了"为什么"？
- [ ] 代码块是否完整、语言标注正确？（C 代码用 `c`，shell 命令用 `bash`，配置文件用对应格式如 `yaml`/`toml`/`ini`）
- [ ] 对话中的报错/坑是否被记录在文章中？
- [ ] 总结是否提炼了真正有价值的结论（非复读正文）？
- [ ] 技术术语英文是否保留？中文表达是否自然？
- [ ] 博客是提炼而非对话复述？（不应出现对话式的来回试错过程）

### 最终交付

文件名格式：

```
YYYY-MM-DD-[slug].md
```

其中 slug 为标题的小写英文缩写（用连字符连接），例如：

```
2026-04-05-wsl2-docker-proxy-setup.md
2026-04-05-ccdb-paxos-log-deletion.md
```

保存到 `/mnt/user-data/outputs/`，用 `present_files` 提供下载链接。

对话中的最终输出只包含：
1. 一句话确认交付完成
2. 下载链接
3. 如果读者视角检查发现了问题并修复，简要说明修复了什么

## 博客模板

### 类型 A：教程 / How-to

**固定骨架：**

```
# [标题：动词开头，说明做什么，包含具体技术栈名，如"在 WSL2 中配置 Docker 代理"]

> **核心目的**：一句话点明做这件事能解决什么问题。
> 讲人话：[用更口语的方式再说一遍，降低理解门槛]

## 背景与目标          ← 必须有
[为什么需要做这件事？不做会有什么问题？完成后达到什么效果]

## 环境与前提          ← 按需，若无依赖可省略
[操作系统版本、依赖工具、前置条件]

## [核心步骤章节]      ← AI 自由划分，通常 2-5 个步骤章节

每个步骤的内部节奏：
  1. 先给完整命令/配置代码块
  2. 解释关键行"是如何工作的"（不是每行都解释，只解释不直觉的地方）
  3. 给出预期输出（如果有）

## 常见问题            ← 按需，若对话中有踩坑记录则必须包含
[用"**遇到 XXX 报错怎么办？**"格式设悬念，然后给出解决方案]

## 总结                ← 必须有
[一句话精华：这个方案的核心价值是什么]
```

**写作规范：**
- 开头 blockquote 必须有"讲人话"的通俗解释，让读者秒懂这篇文章解决什么问题
- 命令/配置用代码块，注意事项用 `> ⚠️` blockquote，两种格式不混用
- 语气：直接，面向已有一定基础的工程师，不写"接下来我们..."这类废话
- 每个步骤结束后展示预期输出，读者可以对照验证

---

### 类型 B：技术深度解析

**固定骨架：**

```
# [标题：名词短语，说明分析对象，包含具体技术名，如"CCDB Paxos 日志删除机制解析"]

> **核心结论**：用一句话点明这个机制/技术的本质是什么。
> 讲人话：[用更口语的方式再说一遍]

## 问题背景            ← 必须有
[按因果链组织：出了什么问题 → 最直接的修法 → 为什么没用 → 实际方案 → 哪里出了问题]
[不需要每步都有，但因果链不能断：读者看完背景应该清楚"为什么要读这篇文章"]

## [核心机制/实现]     ← AI 自由划分，通常 2-4 个章节

每个章节的内部节奏（参考 X-Macro 文章的 Step 结构）：
  1. 给出核心代码/设计/结构
  2. 用"**XXX 是如何工作的？**"设悬念
  3. 逐步拆解执行过程（可以用 1/2/3 有序步骤）
  4. 给出"最终展开/执行结果"，形成前后对比

可选章节（按需）：
  - 关键细节 / 边界情况
  - 与同类方案的对比（如"为什么不用 XXX？"）
  - 踩坑记录

## 总结                ← 必须有

用"普通写法 vs 本文方案"的对比格式，强化"为什么要这样做"：

**普通写法：**
1. [描述普通写法的第一步]
2. [描述普通写法的典型问题——漏掉某步、需要重复维护等]
3. 结果：[出什么错，或者维护成本高在哪]

**[本文方案]写法：**
1. [只需要做什么]
2. [其他的自动搞定]
3. 结果：[绝对不会出现 XXX 问题]

最后一行：**[核心概念]**：一句话提炼本文技术的本质思想。
```

**写作规范：**
- 开头 blockquote 的"讲人话"是关键：把晦涩的技术用一句大白话解释清楚
- 问题背景必须展示"痛点代码"——让读者看到不用这个技术时有多麻烦
- 每个章节分析时，先展示代码，再用"**XX 是如何工作的？**"引出解释，最后展示"最终生成/展开的结果"
- 总结部分强制使用"普通写法 vs 新方案"对比，强化读者对方案价值的认知
- 技术术语保留英文（Paxos、WAL、LWT、epoch），但首次出现时用括号补充一句中文说明

---

## 通用写作规范

教程和技术解析都适用：

- **反 AI 腔调**：标题和小标题用平实描述，不用夸张修辞或戏剧化表述；"讲人话"层简短自然，不刻意造比喻；不用排比句式堆砌气势
- **术语忠实度**：用用户和原始代码中已有的术语描述代码，不强加自己的分析框架
- **代码风格匹配**：示例代码匹配原始 codebase 的语言和编码风格（语言、命名规范、使用的库/接口）
- **信息密度**：博客是提炼而非对话复述。不应出现明显的对话式来回过程；如果博客中某段内容无法追溯到对话中的具体知识点，则属于 AI 填充，应删除

---

## 偏差处理

| 用户行为 | 应对策略 |
|---------|---------|
| "快速出一篇" / "别问了直接写" | 切换快速模式，跳过交互 |
| 在大纲阶段说"差不多就行" | 视为确认，直接进入生成 |
| 只想改当前输出（"这段重写一下"） | 用 `str_replace` 局部修改，不触发 skill-iterate |
| 提供了额外上下文（"还有个背景你不知道..."） | 纳入博客，更新对应章节 |
| 对话内容太散，不适合单篇博客 | 主动建议拆分为多篇，让用户选择先写哪篇 |
| 对话内容太少，不足以撑起一篇博客 | 坦诚告知，建议写成短笔记而非博客，或补充更多内容 |

## 🔁 自迭代评估标准

> 由 skill-iterate 元 skill 读取。本 section 不影响博客生成流程。
> 描述本 skill 输出的质量评估维度，供人工标注时对照使用。

```yaml
sample_description: |
  一段技术对话（input）+ 对应生成的博客 Markdown（output）。
  教程类和技术解析类各需要至少一个样本。

rubric:
  structure_completeness:
    weight: 0.20
    pass_threshold: 7.0
    criteria: |
      根据博客类型检查所有「必须有」的章节是否存在且内容完整。
      教程必须有：背景与目标、至少一个核心步骤章节、总结。
      技术解析必须有：问题背景（含痛点）、核心机制章节、总结（含普通 vs 新方案对比）。
      缺少必须章节每个扣 2 分；章节存在但内容空洞（如只有标题没有实质内容）每个扣 1 分。

  opening_blockquote:
    weight: 0.15
    pass_threshold: 7.0
    criteria: |
      开头 blockquote 必须有两层：①核心结论/目的；②「讲人话」（口语零门槛）。
      「讲人话」合格标准：初中生能听懂，不出现任何技术术语。
      缺少「讲人话」层扣 4 分；「讲人话」仍含技术术语扣 2 分；无 blockquote 扣满（0 分）。

  formatting_discipline:
    weight: 0.15
    pass_threshold: 7.0
    criteria: |
      命令/配置必须用代码块（```）且语言标注正确（c/bash/yaml 等，不使用泛化的 text）；
      注意事项/警告必须用 `> ⚠️` blockquote。
      两种格式不混用：注意事项不进代码块，命令不进 blockquote。
      每处格式错误扣 1.5 分。

  information_density:
    weight: 0.20
    pass_threshold: 6.5
    criteria: |
      博客是提炼，不是对话复述。四项检查：
      ① 去掉了来回试错的冗余交互（明显复读扣 3 分）
      ② 关键代码/命令/配置完整保留（丢失一处扣 2 分）
      ③ 对话中出现的报错和解决方案被记录（漏掉一处扣 1.5 分）
      ④ 博客中无法追溯到对话具体知识点的段落视为 AI 填充（每处扣 2 分）

  reader_accessibility:
    weight: 0.15
    pass_threshold: 6.5
    criteria: |
      从外部读者视角检查可读性：
      ① 技术术语首次出现时有简要说明（缺失每处扣 1 分）
      ② 无未解释的前置知识跳跃——读者不应需要对话上下文才能理解某段内容（每处扣 2 分）
      ③ 代码片段有足够的上下文（文件路径、函数签名、调用场景）（缺失每处扣 1.5 分）
      ④ 因果链完整——读者能仅凭博客理解"为什么要这样做"（断裂每处扣 2 分）

  hook_pattern:
    weight: 0.15
    pass_threshold: 6.0
    criteria: |
      仅技术解析类博客检查此维度，教程类直接给 10 分。
      核心机制章节内部必须使用「XXX 是如何工作的？」引出拆解，
      最终给出执行结果/展开结果形成前后对比。
      应该用但未用此模式的章节每个扣 2 分。

convergence_threshold: 8.0
max_rounds: 5
```
