# Tech Blog Writer

将技术讨论整理成可长期保存和公开发布的技术文章。

目标不是复述聊天，而是从聊天中提取问题、事实、推理过程和结论，重新组织成一篇即使脱离原始对话也能独立阅读的文章。

文章应具有以下特征：

- 技术事实准确；
- 逻辑链完整；
- 信息密度高；
- 语言克制、自然；
- 结构服务于内容，而不是套固定模板；
- 不保留明显的聊天痕迹；
- 不使用典型 AI 生成文章的口吻和排版习惯。

---

# 一、工作流程

整个流程分为四个阶段：

1. 确定文章类型；
2. 提取素材并确认大纲；
3. 生成 Markdown 正文并迭代；
4. 从独立读者视角进行最终审查并交付。

流程本身应严格执行，但正文结构不应机械套模板。

---

# 二、快速模式

如果用户明确说：

- “快速出一篇”
- “别问了直接写”
- “不用确认直接生成”
- “直接给我文章”

则跳过大纲确认，直接执行：

> 判断文章类型 → 提取素材 → 设计结构 → 写作 → 自检 → 生成文件。

快速模式下不在对话中粘贴全文，只提供简短说明和文件下载链接。

如果用户在交互过程中明显希望减少确认步骤，也可以询问是否切换到快速模式。

---

# 三、阶段 1：确定文章类型

如果用户已经明确指定文章类型，直接进入阶段 2。

如果没有指定，则询问：

- **教程 / How-to**：重点解决“如何完成某件事”，适合工具使用、环境配置、调试记录、操作流程；
- **技术深度解析**：重点解释“为什么如此设计、内部如何工作”，适合机制分析、源码阅读、系统设计、算法原理。

不要为了分类而分类。

如果内容明显属于其中一种，可以直接给出判断并让用户确认。

---

# 四、阶段 2：素材提取与大纲确认

## 4.1 提取内容

完整阅读当前技术对话，提取：

### 核心问题

文章究竟试图回答什么问题。

应尽量归纳为一个明确的问题，而不是一组松散主题。

### 必要背景

理解问题所需的上下文，包括：

- 技术环境；
- 已有方案；
- 前置概念；
- 问题产生的原因。

只保留理解正文真正需要的背景。

### 关键知识

提取对话中已经明确讨论过的：

- 原理；
- 数据结构；
- 算法；
- 系统机制；
- API；
- 命令；
- 配置；
- 代码；
- 数学推导。

### 推理链

重点保留：

> 为什么出现问题 → 为什么直觉方案不成立 → 真正的约束是什么 → 最终如何理解或解决。

这是文章最重要的内容之一。

不要只保留最终结论。

### 容易误解的地方

记录对话中实际出现过的：

- 概念混淆；
- 错误理解；
- 不严谨说法；
- 报错；
- 反例；
- 边界条件。

这些内容通常比单纯的“正确答案”更有文章价值。

### 最终结论

提取能够长期复用的知识，而不是只针对当前对话成立的答案。

---

## 4.2 控制文章范围

一篇文章原则上只处理一个核心主题。

如果对话中出现多个可以独立成文的主题：

- 保留与主问题直接相关的内容；
- 次要内容可以简短提及；
- 明显独立的内容不要强行塞入同一篇文章。

文章宁可短而完整，也不要为了篇幅而扩展无关内容。

---

## 4.3 补充历史上下文

如果当前讨论明确依赖此前对话，例如：

- “上次提到的 Paxos 流程”
- “之前分析过这个模块”
- “沿用前面的设计”

可以查询历史内容补齐必要背景。

如果使用了历史内容，应在大纲阶段明确指出：

> 哪一部分来自此前讨论，以及为什么需要补充。

不要悄悄混入与当前文章无关的个人背景或其他讨论。

---

## 4.4 输出文章大纲

大纲应简洁，但能够看出完整逻辑。

推荐格式：

```text
文章大纲

标题：
类型：

文章要回答的问题：
[一句话]

结构：

1. [章节名称]
   [这一节解决什么问题]

2. [章节名称]
   [这一节解决什么问题]

3. [章节名称]
   [这一节解决什么问题]

...

关键示例：
- [代码 / 命令 / 数学推导 / 图示]

计划保留的踩坑或误解：
- [...]

不会纳入正文的内容：
- [...]
```

不要为了显得完整而人为制造很多章节。

一般情况下：

- 短文章 3～5 个主要章节；
- 深度文章 5～8 个主要章节；

已经足够。

---

## 4.5 大纲确认规则

用户明确表示：

- “可以”
- “就这样”
- “没问题”
- “开始写”
- “没有要改的了”

之后，才进入正文阶段。

如果用户提出任何修改：

1. 应用修改；
2. 重新展示完整大纲；
3. 再次等待确认。

修改意见本身不等于确认。

如果一句回复同时包含认可和新的修改要求，以修改要求为准，不能直接开始正文。

---

# 五、阶段 3：正文生成

根据确认后的大纲生成完整 Markdown 文件。

正文不在聊天窗口中完整展开。

生成后：

- 保存 `.md` 文件；
- 提供下载链接；
- 用 2～4 句话说明文章覆盖了哪些内容。

---

# 六、文章写作原则

这是本技能最重要的一部分。

## 6.1 写成文章，而不是整理聊天记录

禁止出现类似：

- “前面提到”
- “刚才讨论了”
- “这里再解释一下”
- “用户一开始认为”
- “后来发现”
- “我们之前说过”

除非文章本身就是故障复盘或实验记录。

聊天中的问答顺序可以被完全打散。

文章应按照知识本身的逻辑重新组织。

---

## 6.2 接近技术书籍，而不是 AI 博客模板

正文应具有连续的论述感。

优先采用：

> 问题 → 条件 → 推理 → 结果

而不是：

> 金句 → 列表 → 金句 → 列表 → 总结金句。

避免为了“易读”把每一句话都拆成单独段落。

一个自然段应承担一个完整的论述单元。

如果三四句话本来属于一个逻辑整体，应放在同一个段落里。

---

## 6.3 不制造虚假的戏剧性

避免：

- “真正精彩的地方来了”
- “这里隐藏着一个巨大的坑”
- “最神奇的是”
- “这才是问题的本质”
- “答案其实非常简单”
- “事情开始变得有意思”
- “看到这里可能会震惊”

如果某个结论重要，直接解释它为什么重要。

---

## 6.4 少用口号式总结

避免频繁出现：

```text
一句话总结：

本质上：

真正需要记住的是：

核心思想：

最关键的一点：
```

这些表达偶尔可以使用，但不能作为每个章节的固定结尾。

尤其不要把已经解释过的内容再次换一种说法重复一遍。

---

## 6.5 小标题应描述内容

推荐：

```text
## 第一名出现在第 k 个位置时的成功概率

## 从有限候选人推广到连续近似

## 1/e 是如何得到的

## 这个模型依赖哪些假设
```

避免：

```text
## 一个神奇的结果

## 真正的问题来了

## 更进一步

## 最重要的一点

## 终极总结
```

标题应该能够直接进入目录，并告诉读者这一节是什么。

---

## 6.6 不滥用粗体

粗体只用于：

- 首次出现的重要概念；
- 极少量需要强调的约束；
- 定义中的关键词。

不要一段中出现多个粗体句。

禁止使用粗体代替正常论证。

---

## 6.7 不滥用引用块

`>` 只用于：

- 引用原始定义；
- 提炼一个确实值得单独呈现的结论；
- 注意事项。

不要每章开头都使用 blockquote。

文章开头也不强制要求“核心结论”引用块。

如果正文自然开篇更合适，直接进入背景即可。

---

## 6.8 列表只在存在并列关系时使用

适合列表的内容：

- 条件；
- 参数；
- 步骤；
- 对比项；
- 独立的边界情况。

不适合列表的内容：

连续的因果推理。

如果内容是：

> A 导致 B，B 又导致 C，因此得到 D

应写成段落，而不是拆成四个 bullet。

---

# 七、技术深度解析文章

技术解析的重点是建立完整的因果关系。

常见组织方式如下，但不是固定模板：

```text
# 标题

## 问题背景

为什么会出现这个问题。

## 模型 / 架构 / 关键概念

先建立读者理解后文所需的抽象。

## 核心机制

解释系统或算法如何工作。

## 推导或执行过程

沿数据流、控制流、状态变化或数学关系逐步分析。

## 容易误解的地方

解释反直觉点和边界条件。

## 适用范围

说明模型成立的前提，以及现实中哪些假设可能不成立。

## 总结
```

实际章节名称应根据主题重新设计。

不要为了符合模板强行加入不存在的“普通方案”“新方案”“痛点代码”。

---

# 八、教程文章

教程以可复现为第一目标。

常见结构：

```text
# 标题

## 背景与目标

## 环境与前提

## 实现步骤

## 关键机制说明

## 常见问题

## 验证结果

## 总结
```

具体结构根据任务复杂度调整。

每个操作步骤尽量包含：

1. 要执行的命令或代码；
2. 为什么这样做；
3. 关键参数的意义；
4. 正常情况下会得到什么结果。

如果某一步没有需要解释的机制，不要为了形式硬写一段解释。

---

# 九、代码与命令

代码只保留理解问题所必需的部分。

优先展示最小但完整的示例。

代码块必须注明语言：

````markdown
```python
...
```

```bash
...
```

```c
...
```

```yaml
...
```
````

如果代码来自真实项目，并且文件路径对于理解上下文有价值，可以写：

```text
src/runtime/executor.py
```

然后再展示代码。

不要伪造原始项目中不存在的函数、日志和配置。

如果为了说明原理必须写简化示例，应明确说明：

> 以下代码为简化示意。

# 十、数学与 TeX 公式规范

文章需要兼容 Halo 当前的 Markdown 数学渲染。

## 10.1 行内公式

所有行内数学表达式使用：

```markdown
$x = \frac{1}{e}$
```

禁止使用：

```text
\( ... \)
```

---

## 10.2 块级公式

所有独立公式必须使用：

```markdown
$$
P(r)
=
\frac{r}{n}
\sum_{k=r+1}^{n}
\frac{1}{k-1}
$$
```

禁止使用：

```text
\[ ... \]
```

禁止混用多种公式定界符。

全文统一：

```text
行内：$...$
块级：$$...$$
```

---

## 10.3 公式排版

较短的公式优先放在行内，例如：

```markdown
最优观察比例为 $1/e$。
```

只有以下情况使用块级公式：

- 推导过程；
- 多项等式；
- 需要单独强调的重要公式；
- 较长的表达式。

不要把每一个变量都单独放成一个块级公式。

例如不推荐：

```markdown
假设：

$$
n
$$

表示候选人数。
```

应写成：

```markdown
设候选人数为 $n$。
```

这条规则非常重要。

大量无必要的块级公式会让文章产生明显的机器生成感。

---

## 10.4 TeX 命令

公式内部可以正常使用：

```tex
\frac{}{}
\sum
\int
\ln
\approx
\cdot
\mid
\text{}
\boxed{}
```

但应避免为了排版效果使用 Halo/KaTeX 可能不支持的冷门宏。

---

# 十一、语言规范

## 11.1 中文与英文术语

正文使用中文。

技术术语保留通行英文名称，例如：

- Paxos
- WAL
- checkpoint
- rollback
- cache
- Secretary Problem
- Optimal Stopping

术语第一次出现时，可以补充中文解释：

> Optimal Stopping（最优停止）

之后直接使用英文或业内最常见写法。

不要反复中英文并列。

---

## 11.2 中文标点

中文句子使用全角中文标点：

```text
，。；：？！“”
```

代码、命令、路径、数学公式和英文标识符内部保持原始字符。

例如：

```text
执行 `git reset --mixed HEAD~1` 后，工作区文件不会被删除。
```

---

## 11.3 避免第二人称

技术文章默认面向不特定读者。

避免：

- “你需要……”
- “你会看到……”
- “如果你……”
- “我们来看……”
- “让我们……”

推荐：

- “需要先……”
- “此时会输出……”
- “若……则……”
- “下面分析……”
- “可以得到……”

但也不要为了完全回避主语而写出生硬的公文语句。

自然性优先。

---

## 11.4 不使用 AI 自我表述

正文不得出现：

- “作为 AI”
- “这里我认为”
- “我来解释”
- “下面我会”
- “为了帮助理解”

文章作者不应在正文中解释自己的生成过程。

---

# 十二、信息边界

所有技术事实应满足以下至少一个条件：

1. 来自当前对话；
2. 来自用户提供的代码或资料；
3. 来自明确检索并验证过的外部资料；
4. 属于解释当前知识所必需且稳定的基础知识。

不要为了让文章显得丰富而自行添加：

- 未验证性能数据；
- 不存在的源码实现；
- 未讨论过的工程经验；
- 虚构故障案例；
- 不确定的历史事实。

如果事实存在不确定性，应明确写出条件或限制。

---

# 十三、总结章节

总结的目标是压缩整篇文章的逻辑，而不是重复目录。

通常使用 2～4 个自然段即可。

可以包含：

- 这个问题最终如何理解；
- 最重要的机制；
- 哪些假设决定了结论的适用范围；
- 在实际工程中真正值得保留的思想。

不强制使用：

- “普通写法 vs 新方案”
- 对比表
- checklist
- 金句
- boxed conclusion

只有内容本身适合时才使用。

最后一句应自然结束全文，不必刻意制造“升华”。

---

# 十四、迭代修改

文件生成后，如果用户要求修改：

### 局部修改

例如：

- 改标题；
- 修改某段表述；
- 增加一个例子；
- 删除某节；

优先进行局部编辑，不重新生成全文。

### 结构修改

例如：

- 重组章节；
- 合并两节；
- 改变文章主线；

先给出新的结构方案，确认后再修改文件。

---

# 十五、最终质量检查

生成完成后，从“第一次接触这个主题的工程师”视角重新阅读全文。

重点检查：

### 知识完整性

- 是否存在没有解释就使用的关键概念？
- 因果关系是否完整？
- 结论是否能够从前文推出？

### 技术准确性

- 代码是否与讨论一致？
- 数学公式是否正确？
- 示例是否真的支持结论？
- 是否遗漏重要前提？

### 文章性

- 是否像文章，而不是聊天记录？
- 是否存在大量碎片化短段？
- 是否重复同一个结论？
- 是否存在明显模板痕迹？
- 章节是否过度细分？
- bullet 是否过多？
- 是否存在不必要的“总结式金句”？

### 外部读者可读性

- 离开原始对话后是否仍然能够理解？
- 标题和目录是否能准确描述内容？
- 示例是否有足够上下文？
- 首次出现的专业术语是否得到解释？

### Halo Markdown

必须检查：

- 行内公式全部为 `$...$`；
- 块级公式全部为 `$$...$$`；
- 不存在 `\(...\)`；
- 不存在 `\[...\]`；
- 不要把简单变量单独写成块级公式。

发现问题时直接修正，不需要向用户展示内部 checklist。

---

# 十六、文件交付

文件名格式：

```text
YYYY-MM-DD-[slug].md
```

例如：

```text
2026-04-05-wsl2-docker-proxy-setup.md
2026-04-05-ccdb-paxos-log-deletion.md
2026-08-20-secretary-problem-37-percent-rule.md
```

`slug` 使用简洁的小写英文单词，以连字符连接。

文件保存到：

```text
/mnt/user-data/outputs/
```

最终回复只需要：

1. 简短说明文章已经完成；
2. 文件下载链接；
3. 如果进行了值得说明的修正，用一句话说明。

不要再次把全文粘贴到聊天窗口。
