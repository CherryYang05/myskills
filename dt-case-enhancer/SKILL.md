# DT用例增强Skill

这是一个专门为DT(开发者自测试)用例增强补齐设计的skill,采用思维链(CoT)方法将复杂的增量用例开发分解为多个可管理的步骤。

## 适用场景

- 对已有DT用例进行增强补齐
- 识别存量用例中遗漏的测试场景
- 补充增量DT测试用例
- 需要使用GTEST框架和MOCKCPP打桩的测试增强

## 与dt-case-generator的区别

| 特性 | dt-case-generator | dt-case-enhancer |
|------|------------------|------------------|
| 适用场景 | 从零生成DT用例 | 对已有DT用例进行增强补齐 |
| 步骤0信息收集 | 3个路径 | 4个路径 (+存量DT用例目录) |
| 步骤2 | 用例场景分析 | 全量场景用例设计 |
| 步骤3 | 识别打桩流程 | 存量DT用例分析 |
| 步骤4 | 用例代码生成 | 增量场景用例分析 (含对比报告) |
| 步骤5 | 编译脚本适配 | 生成DT用例 |
| 步骤6 | 用例编译 | 编译 |
| 步骤7 | 用例执行和调试 | 用例执行和调试 |
| 用例数量限制 | 50个 | 20个 |
| Subagent使用 | 部分步骤 | 所有7个步骤 |
| 对比报告 | 无 | 已覆盖场景对比报告 |

## 核心原则

### 1. 真正的交互式确认 (最重要原则)

**这是绝对不能违反的原则**:
- 每次询问用户问题后,必须**真正停下来等待用户回复**
- **绝不能自问自答**
- **绝不能自动假设用户的答案**
- **绝不能在用户回复之前继续下一步**
- **每一步都使用subagent的方式执行,减少上下文干扰**
- **如果某一步任务失败,则必须使用subagent的方式重试该步骤,如果重试5次失败则停下等用户接管**
- 必须看到用户明确的回复后才能继续

### 2. 计划制定阶段 (Plan Mode)

**步骤0之后必须进入计划制定阶段**:
- 步骤0收集完4个信息后,不能直接进入步骤1
- 必须进入plan模式,与用户制定详细的执行计划
- 通过问答方式完善计划,确保双方共识
- 用户确认计划后,自动退出plan模式,进入步骤1
- 计划制定阶段由主agent直接与用户交互,不使用subagent

### 3. 明确的停止指令

**在每个需要用户确认的地方,使用以下明确的停止指令**:
```
请回答以上问题,我会等待你的回复,不会自动继续。
```
或者:
```
请确认以上信息,回复"继续"或"确认"后我会进行下一步。
```

### 3. Subagent使用策略

所有7个步骤都必须使用subagent,每个subagent使用描述性名称:

| 步骤 | Subagent名称 | 任务 |
|------|-------------|------|
| 步骤0 | info-collector | 收集4个路径信息 |
| 计划制定 | 无 | 主agent与用户交互,制定执行计划 |
| 步骤1 | code-analyzer | 代码理解 |
| 步骤2 | full-scenario-designer | 全量场景用例设计 |
| 步骤3 | existing-case-analyzer | 存量DT用例分析 |
| 步骤4 | incremental-scenario-analyzer | 增量场景用例分析 |
| 步骤5 | test-case-generator | 生成DT用例 (可能多个) |
| 步骤6 | compiler | 编译 |
| 步骤7 | test-suite-debugger | 调试测试套 (可能多个) |

**Subagent执行规则**:
- 所有7个步骤都必须使用subagent
- 计划制定阶段由主agent直接与用户交互,不使用subagent
- Subagent之间串行执行,不能并行
- 每个subagent完成后返回主agent
- 主agent等待用户确认后,启动下一个subagent
- 步骤5和步骤7可能需要多个subagent (按批次拆分)

## 用户体验优化: 使用可点击选项

**重要**: 在需要用户确认或选择的场景中,必须使用`question`工具提供可点击选项,而不是让用户手动输入。

### Question工具使用场景

1. **步骤确认**: 当完成一个步骤后,询问用户是否继续
2. **选项选择**: 当需要从多个选项中选择一个时
3. **决策确认**: 当需要用户做出决策时
4. **错误处理**: 当遇到问题时,询问用户如何处理

### Question工具使用示例

**示例1: 步骤确认**
```markdown
步骤1代码理解已完成。是否继续进行步骤2(全量场景用例设计)?

请使用question工具询问用户:
- 选项1: 继续,进入步骤2
- 选项2: 修改,重新生成步骤1
- 选项3: 停止,查看当前结果
```

**示例2: 选项选择**
```markdown
发现了3个需要补充的场景,请选择处理方式:

请使用question工具询问用户:
- 选项1: 生成所有场景的用例
- 选项2: 只生成高优先级场景的用例
- 选项3: 手动选择要生成的场景
```

**示例3: 错误处理**
```markdown
编译失败,发现以下错误:
- 错误1: ...

请使用question工具询问用户:
- 选项1: 自动修复并重新编译
- 选项2: 人工指导修复
- 选项3: 跳过编译,继续下一步
```

### Question工具使用规则

1. **必须使用question工具**: 在需要用户确认或选择时,必须使用question工具
2. **提供明确的选项**: 选项应该清晰、具体、易于理解
3. **设置合适的默认选项**: 根据上下文设置合理的默认选项
4. **支持多选**: 如果需要,可以设置`multiple: true`支持多选
5. **提供选项描述**: 为每个选项提供简短的描述,帮助用户理解

### 步骤0: 收集基本信息

在开始之前,必须先收集以下信息:

**必须询问用户的4个问题:**
1. 模块的代码目录在哪里?(绝对路径或相对路径)
2. 对外头文件目录在哪里?(绝对路径或相对路径)
3. DT测试代码的输出目录在哪里?(绝对路径或相对路径)
4. 存量DT用例目录在哪里?(绝对路径或相对路径)

**操作流程:**
1. 启动 info-collector subagent
2. 向用户提出上述4个问题
3. **重要**: 必须明确告诉用户需要回答这些问题
4. **重要**: 必须明确表示会等待用户回复
5. **重要**: 绝不能自问自答,绝不能假设任何答案
6. 等待用户回答所有问题
7. 确认信息无误后,进入**计划制定**阶段

### 计划制定阶段 (Plan Mode)

**目标**: 与用户制定详细的执行计划,确保双方对后续步骤有清晰的共识

**操作流程:**
1. **展示收集到的信息**
   - 列出步骤0收集到的4个路径信息
   - 使用question工具确认信息是否正确
     - 选项1: 信息正确,制定计划
     - 选项2: 修改信息
     - 选项3: 重新开始

2. **制定初步计划**
   - 展示完整的7步骤流程概述
   - 说明每个步骤的主要目标和预期输出
   - 使用question工具询问用户是否需要调整计划
     - 选项1: 计划合理,继续完善
     - 选项2: 需要调整计划
     - 选项3: 需要跳过某些步骤

3. **完善计划细节** (通过问答方式)
   - 询问是否有特殊要求或关注点
   - 使用question工具询问用户:
     - 选项1: 有特殊要求,需要说明
     - 选项2: 无特殊要求,继续
   - 如果选择"有特殊要求",等待用户详细说明

4. **确认执行策略**
   - 使用question工具询问用户:
     - 选项1: 按标准流程执行所有7个步骤
     - 选项2: 只执行部分步骤(需说明具体步骤)
     - 选项3: 重点关注某些步骤(需说明具体步骤)

5. **确认计划**
   - 展示最终确定的执行计划
   - 使用question工具确认:
     - 选项1: 确认计划,开始执行
     - 选项2: 修改计划
     - 选项3: 取消执行

6. **退出plan模式**
   - 只有在用户选择"确认计划,开始执行"后,才退出plan模式
   - 自动进入步骤1,启动code-analyzer subagent

**正确的对话示例:**
```
我: 已收集到以下信息:
1. 模块的代码目录: fusion/product/taishan_src/fdsa/src/plugins/link_subhealth
2. 对外头文件目录: fusion/product/taishan_src/fdsa/include
3. DT测试代码的输出目录: fusion/product/test/fdsa/fdsa_dt_linux/dt_src/link_subhealth
4. 存量DT用例目录: fusion/product/test/fdsa/fdsa_dt_linux/dt_src/link_subhealth

3. 步骤3: 存量DT用例分析 - 分析存量DT用例,输出场景覆盖分析
4. 步骤4: 增量场景用例分析 - 对比全量场景和存量用例,识别需要补充的场景

7. 步骤7: 用例执行和调试 - 执行和调试生成的DT用例

您是否需要调整这个计划?

(使用question工具提供选项)

用户选项1: 计划合理,继续完善

我: 您是否有特殊要求或需要重点关注的地方?

(使用question工具提供选项)

用户选项2: 无特殊要求,继续

我: 请确认执行策略:

(使用question工具提供选项)

用户选项1: 按标准流程执行所有7个步骤

我: 最终执行计划:
- 模块: link_subhealth
- 执行步骤: 所有7个步骤
- 用例限制: 最多20个
- 特殊要求: 无

确认后我将开始执行步骤1,是否确认?

(使用question工具提供选项)

用户选项1: 确认计划,开始执行

我: 已确认计划,开始执行步骤1...

(自动退出plan模式,进入步骤1)
```

**重要注意事项:**
1. **必须使用question工具**: 所有用户交互都必须使用question工具提供可点击选项
2. **必须真正等待**: 每次询问后必须真正停下来等待用户回复,绝不能自问自答
3. **必须自动退出**: 用户确认计划后,必须自动退出plan模式,进入步骤1
4. **必须清晰展示**: 每个阶段都要清晰地展示当前状态和下一步操作
5. **必须保留信息**: plan模式收集的所有信息(包括特殊要求、执行策略等)都要传递给后续的subagent

### 步骤1: 理解代码

**目标:** 识别关键接口、结构体和枚举,并生成完整的代码分析文档

**操作流程:**
1. 启动 code-analyzer subagent
2. 代码analyzer生成代码分析文档
3. **重要**: code_analysis.md必须包含以下图表:
   - **标准UML类图** (使用Mermaid classDiagram格式)
   - **接口调用关系图** (使用Mermaid graph格式,展示对外接口、内部函数、外部依赖之间的关系)
   - **关键接口内部序列图** (使用Mermaid sequenceDiagram格式,为3-5个最关键的接口生成详细的内部调用序列)
4. 返回主agent,展示关键信息
5. **重要**: 使用question工具询问用户是否继续
   - 选项1: 继续,进入步骤2(全量场景用例设计)
   - 选项2: 修改,重新生成步骤1
   - 选项3: 停止,查看当前结果
6. 等待用户选择
7. 只有在用户选择"继续"后,才能进入步骤2

**输出文档:**
- `<输出目录>/code_analysis.md`
- **必须包含以下内容**:
  - 标准UML类图 (使用Mermaid格式)
  - **接口调用关系图** (使用Mermaid格式,必须包含在文档中,展示对外接口、内部函数、外部依赖三个子图及调用关系)
  - **关键接口内部序列图** (使用Mermaid sequenceDiagram格式,至少3-5个关键接口,每个序列图包含参与者、调用流程和关键步骤说明,必须包含在文档中)
  - 关键结构体 (包含完整定义和代码位置)
  - 枚举 (包含完整定义和代码位置)
  - 对外接口 (包含完整函数签名和代码位置)
  - 需要打桩的接口

**重要提示:**
- 接口调用关系图和序列图必须直接包含在code_analysis.md中,不能保存为单独文件
- 序列图应该选择最核心、最复杂的接口进行分析
- 序列图需要展示接口内部的函数调用流程,包括参与者、调用方向和关键步骤

- `references/fdsa-project-info.md` - FDSA项目背景信息

   - 选项3: 停止,查看当前结果

### 步骤3: 存量DT用例分析 (关键差异点)

3. 返回主agent,展示关键信息
4. **重要**: 使用question工具询问用户是否继续
   - 选项1: 继续,进入步骤4(增量场景用例分析)

   - 选项3: 停止,查看当前结果

**输出文档:**
- `<输出目录>/existing_test_scenarios_analysis.md`

### 步骤4: 增量场景用例分析 (关键差异点)

**目标:** 对比步骤2和步骤3,识别需要补充的场景用例

**操作流程:**
1. 启动 incremental-scenario-analyzer subagent
2. 对比全量场景和存量用例,识别差异
3. 生成增量场景用例方案
4. 生成已覆盖场景对比报告 (关键)
5. 返回主agent,展示关键信息
6. **重要**: 使用question工具询问用户是否继续
   - 选项1: 继续,进入步骤5(生成DT用例)
   - 选项2: 修改,重新生成步骤4
   - 选项3: 停止,查看当前结果
7. 等待用户选择
8. 只有在用户选择"继续"后,才能进入步骤5

**输出文档:**
- `<输出目录>/incremental_test_scenarios.md` - 增量场景用例方案
- `<输出目录>/coverage_comparison_report.md` - 已覆盖场景对比报告 (关键)

**重要原则:**
> 如果你分析出步骤2中的用例是已在存量代码中已覆盖的,本次不需要补齐,你需要提供明显的证明,防止你分析有误

### 总结
- 已覆盖场景: XX个 (XX%)

### 步骤5: 生成DT用例

**目标:** 生成增量场景的DT用例代码

**操作流程:**
1. 分析用例数量
2. 如果用例数量超过20个,拆分为多个批次
3. 启动 test-case-generator-1 subagent
4. 生成第一批用例
5. 返回主agent,展示结果
6. **重要**: 使用question工具询问用户是否继续
   - 选项1: 继续,生成下一批用例
   - 选项2: 修改,重新生成当前批
   - 选项3: 停止,查看当前结果
7. 等待用户选择
8. 重复上述过程,直到所有批次完成

**任务拆分原则:**
1. 一次只生成一个源文件
2. 一次生成用例不超过20个
3. 如果一个源文件生成超过了20个用例,则进行拆分
4. 拆分时需要把相关的用例一起生成

**输出文档:**
- DT用例代码文件 (.cpp)
- 每个文件不超过20个用例

**详细的提示词模板和操作流程,请参考:**
- `references/prompt-templates.md` - 步骤5: 生成DT用例

### 步骤6: 编译

**目标:** 编译生成的DT用例代码

**操作流程:**
1. 启动 compiler subagent
2. 执行编译命令
3. 分析编译错误
4. 尝试修复 (最多3次)
5. 返回主agent,报告结果
6. **重要**: 如果编译失败,使用question工具询问用户如何处理
   - 选项1: 自动修复并重新编译
   - 选项2: 人工指导修复
   - 选项3: 跳过编译,继续下一步
7. 如果连续3次失败,请求人工指导

**重要原则:**
1. 只能修改DT用例代码,不能修改业务代码
2. 绝对绝对不能删文件和用例
3. 不能删除存量用例
4. 如果AI无法解决编译问题,可以停下等用户人工指导

**详细的提示词模板和操作流程,请参考:**
- `references/prompt-templates.md` - 步骤6: 编译

### 步骤7: 用例执行和调试

**目标:** 执行和调试生成的DT用例

**操作流程:**
1. 按测试套分组
2. 启动 test-suite-debugger-1 subagent
3. 调试第一个测试套
4. 返回主agent,报告结果
5. **重要**: 使用question工具询问用户是否继续
   - 选项1: 继续,调试下一个测试套
   - 选项2: 修改,重新调试当前测试套
   - 选项3: 停止,查看当前结果
6. 等待用户选择
7. 重复上述过程,直到所有测试套完成

**重要原则:**
1. 一次只调试一个测试套,subagent之间串行执行
2. 调试不过的用例,不能修改用户的期望结果,可以把修改方案提出给用户,由用户来决定是否修改
3. 不能擅自修改业务代码,如果用户发现了业务代码问题,给出问题说明和参考解决方案,由用户人工决策
4. 如果AI长期无法解决,则停下说明当前现状,请示用户人工指导

## 常见问题和解决方案

### 问题1: 如何避免重复生成已有用例?
**解答:** 步骤4会生成"已覆盖场景对比报告",提供详细的覆盖理由和证明,确保不会重复生成。覆盖理由会详细说明存量用例的测试逻辑、输入参数、预期输出,解释为什么能覆盖目标场景。

### 问题2: 对比报告中的覆盖理由如何生成?
**解答:** AI会分析存量用例的测试逻辑、输入参数、预期输出,解释为什么能覆盖目标场景。参考 `references/comparison-report-example.md` 查看完整示例。

### 问题3: 用例数量为什么限制为20个?
**解答:** 增强场景通常用例数量较少,更小的粒度可以更精细地控制生成质量,避免上下文过大。

### 问题4: 如何验证对比报告的准确性?
**解答:** 人工审核对比报告,检查覆盖理由是否合理,证明是否充分。每个已覆盖场景都需要提供具体的存量用例名称、文件路径和行号。

### 问题5: AI会偷懒,用例调试不通直接修改检查结果?
**解答:** 提示词里明确不能修改检查结果,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

### 问题6: AI会直接在业务代码中打桩?
**解答:** 人工检查他修改的代码,并在提示词明确不允许修改业务代码,如果调试不通,可以分析下是否业务代码有问题,并给出分析报告。

## 最佳实践

1. **一次只做一件事** - 先让AI把编译调过,然后用例以测试套为粒度进行调试。

2. **当AI自己无法完成任务时,人工定位,并把原因告诉AI** - 让AI来修改,这样后面其它的用例他能能快速解决。

3. **CoreDump类问题,先人工找到堆栈,然后把堆栈给AI** - 这样速度更快。

4. **每一步都要真正等待用户确认,绝不能自问自答** - 这是最重要的交互原则。

5. **提供示例** - 提供one-shot或few-shot示例是最有效的模型引导方法之一。

6. **设计简洁** - 保持提示简明、清晰且易于理解。

7. **明确输出要求** - 清晰定义模型响应的期望格式、长度、风格和内容。

8. **要求提供详细信息** - 必须要求AI提供完整路径、行号、使用位置等详细信息,不能只提供名称。

- [ ] 异常场景是否覆盖

- [ ] 打桩接口都有代码中使用位置
- [ ] 对比报告中的覆盖理由是否充分
- [ ] 是否有重复生成已有用例的情况

## 注意事项

1. **不要修改业务代码** - DT用例应该只测试,不应该修改被测代码
2. **不要删除存量用例** - 只能生成新的增量用例,不能删除或修改存量用例
3. **打桩要合理** - 避免过度打桩导致测试失去意义
4. **检查点要明确** - 每个用例应该有清晰的验证点
5. **用例要可维护** - 避免过于复杂的测试逻辑
6. **每一步都要真正等待用户确认,绝不能自问自答** - 这是最重要的交互原则
7. **绝不能自问自答,绝不能自动假设用户的答案,绝不能在用户回复之前继续下一步**
8. **必须提供详细信息**: 所有接口、结构体、枚举都要有完整路径和行号,打桩接口要有代码中使用位置
9. **对比报告必须详细**: 每个已覆盖场景都需要提供覆盖理由和具体证明
