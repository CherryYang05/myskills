# Skill Iterate

对任意 skill 的输出进行人工标注驱动的自迭代优化。
评估不依赖 LLM 自动打分，而是以**用户的具体标注**作为 ground truth。

---

## 第零步：意图确认（每次触发必做）

收到负反馈时，**先判断用户意图**，不要假设：

> 「你是想：
> A）只修改这次的输出（不影响 skill）
> B）改进 skill，让以后都不再出现这个问题
>
> 选哪个？」

- 用户选 A → **立即终止**，把请求交回原 skill 处理
- 用户选 B → 继续执行下面的步骤

**触发词判断辅助**（语气明确时可以跳过询问直接判断）：

| 语气特征 | 判断 |
|---|---|
| 「以后」「总是」「每次」「记住」+ 负面反馈 | → B，直接进入自迭代 |
| 「重新写」「改一下」「换个说法」 | → A，交回原 skill |
| 不确定 | → 问用户 |

---

## 第一步：确认目标 skill

从上下文推断用户在说哪个 skill。如果对话中明确提到了 skill 名（如"博客 skill"、"llt skill"），直接使用。

确认后，读取该 skill 的 SKILL.md，检查是否包含 `## 🔁 自迭代评估标准` section。

**如果没有该 section：**

> 「`<skill名>` 还没有配置自迭代评估标准，需要先在它的 SKILL.md 末尾加一个 rubric section。
> 你觉得评判这个 skill 输出好坏，最重要的几个维度是什么？」

引导用户定义维度后，生成 rubric section 供用户确认添加，然后继续。

---

## 第二步：收集用户标注

向用户展示当前有问题的输出（对话中已有则直接引用）。

按 rubric 的维度**逐一询问，每次只问一个**：

> 「先看 `<维度名>`：[一句话解释这个维度在检查什么]
> 这次的输出在这里有没有问题？如果有，告诉我：
> - 它写了什么
> - 你期望它写成什么」

收集完一个维度后询问是否继续，用户也可以直接说「够了」跳到分析。

**标注质量要求（不满足则追问）：**
- 必须有具体位置（"第二段"、"讲人话那行"）
- 最好有对比示例（"它写了 X，应该写 Y"）
- 只有情绪没有内容时追问（"写得很差"→「具体哪里差？」）

---

## 第三步：失败定位

将用户标注 + 当前 SKILL.md 一起分析，找出哪条规则不够具体或有歧义导致了失败。

在对话中展示分析结果，请用户确认理解是否准确：

```
失败维度：<维度名>
用户反馈：<原话>
定位规则：SKILL.md "<规则原文片段>"
根因：<为什么这条规则会导致这个问题>
```

如果问题无法定位到现有规则，注明"规则缺失"。

---

## 第四步：提出补丁方案

根据根因分析，提出对 SKILL.md 的最小化修改，以 diff 格式展示：

```diff
- 开头 blockquote 必须有"讲人话"的通俗解释，让读者秒懂这篇文章解决什么问题
+ 开头 blockquote 必须有"讲人话"的通俗解释。
+ 讲人话标准：初中生能听懂，不出现任何技术术语。
+ 反例（不合格）：「通过修改 LIF 配置实现 TLS 协议切换」
+ 正例（合格）：「让两台机器通信时加密，防止被偷听」
```

**补丁原则：**
- 只改导致失败的那条规则，不动其他部分
- 优先用"反例/正例"强化规则，而不是重写规则
- 规则缺失时在最相关章节末尾追加

---

## 第五步：等待用户确认

> 「确认后我会更新 `<skill名>` 的 SKILL.md，这将影响之后所有用这个 skill 生成的内容。确认修改？」

- 确认 → 第六步
- 需要调整 → 回第四步
- 否定 → 放弃本轮，询问是否重新分析

**不得在未收到明确确认的情况下修改任何 SKILL.md。**

---

## 第六步：应用补丁

修改目标 skill 的 SKILL.md 对应章节，完成后告知：

> 「已更新 `<skill名>` 的 SKILL.md（修改了：<维度名> 对应的规则）。」

---

## 第七步：验证（可选）

> 「要用同一段对话重新生成一次，验证改动是否有效吗？」

用户选是 → 调用原 skill 重新生成，请用户对比。

---

## 第八步：收敛与同步

> 「还有其他维度需要改进吗？」

有 → 回第二步继续收集。
没有 → 本轮结束，询问是否通过 skill-sync 推送到 GitHub。

在对话中维护简单的改动日志，防止多轮后遗忘：

```
轮次 1：opening_blockquote → 加了禁止技术术语约束 + 反例/正例
轮次 2：information_density → 明确对话中的报错必须完整保留
```

---

## 硬性约束

- **不改 rubric section 本身**，除非用户明确说"这个维度定义有问题"
- **每次只修一个维度**，无法判断哪个改动生效时不要批量修改
- **不重新组织 SKILL.md 章节结构**，只在对应位置追加或替换
